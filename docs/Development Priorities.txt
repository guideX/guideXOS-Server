================================================================================
guideXOS Server - Development Priorities & Roadmap
================================================================================

Version: 2.0
Last Updated: 2025
Status: Active Development

This document outlines the prioritized development roadmap for guideXOS Server,
reorganized with an SDK-first approach to enable developer adoption.

================================================================================
EXECUTIVE SUMMARY
================================================================================

guideXOS is a multi-architecture operating system with a "no architecture left
behind" philosophy. The development priorities are organized to maximize
developer adoption while building toward the vision of universal applications.

PRIORITY ORDER:
1. Developer SDK & Toolchain (CRITICAL - enables everything else)
2. Universal Binary System (.gxapp format)
3. System APIs & Libraries
4. Package Management
5. Networking & Services
6. ABI Translation (future)

================================================================================
SUPPORTED ARCHITECTURES
================================================================================

Tier 1 (Initial Focus - MVP):
  - x86      32-bit Intel/AMD, Legacy BIOS
  - amd64    64-bit x86-64, UEFI
  - riscv64  64-bit RISC-V (emerging, strategic importance)

Tier 2 (Post-MVP Expansion):
  - arm64    64-bit ARM (AArch64)
  - ia64     Intel Itanium
  - sparc64  64-bit SPARC v9

Tier 3 (Full Support):
  - arm      32-bit ARM (ARMv7)
  - sparc    32-bit SPARC v8
  - ppc64    64-bit PowerPC
  - mips64   64-bit MIPS
  - loongarch64  64-bit LoongArch

================================================================================
PRIORITY 1: DEVELOPER SDK & TOOLCHAIN
================================================================================
Status: HIGH PRIORITY
Phase: 8b
Dependencies: None
Est. Duration: 6-8 weeks

Without a developer SDK, no applications can be built for guideXOS. This is the
single most critical piece of infrastructure.

DELIVERABLES:
-------------

1.1 guideXOS SDK Structure
    /opt/guidexos-sdk/
    ??? bin/           # Developer tools (gxbuild, gxpackage, gxrun)
    ??? include/       # Headers (guidexos/, posix/)
    ??? lib/           # Per-architecture libraries
    ?   ??? x86/       # libc.a, libguidexos.a, crt0.o
    ?   ??? amd64/
    ?   ??? riscv64/
    ??? toolchain/     # Cross-compiler wrappers
    ??? share/         # Templates, examples, docs

1.2 musl libc Integration
    - Port musl libc for each target architecture
    - Modify syscall backend to call guideXOS native syscalls
    - Static linking only (for self-contained universal binaries)
    - Target: Full POSIX.1-2017 compatibility

1.3 Cross-Compiler Toolchain
    Primary: LLVM/Clang (single toolchain, multiple targets)
    Fallback: GCC cross-compilers where needed
    
    Wrapper Scripts:
    - x86-guidexos-clang
    - amd64-guidexos-clang
    - riscv64-guidexos-clang

1.4 System Call Interface
    Dual ABI approach:
    
    A) Native guideXOS Syscalls (preferred for new apps)
       - gxos::sys_open(), gxos::sys_read(), etc.
       - Clean, modern API
       - Full access to guideXOS features
    
    B) POSIX Compatibility Layer (for porting existing software)
       - open(), read(), write(), fork(), exec()
       - Implemented via musl, wraps native syscalls
       - Enables porting of Unix software

1.5 Developer Workflow
    Goal: Simple, one-command builds
    
    # Compile for single architecture
    gxbuild build hello.cpp
    
    # Compile for multiple architectures
    gxbuild build hello.cpp --targets x86,amd64,riscv64
    
    # Create universal package
    gxbuild build hello.cpp --targets x86,amd64 --package -o hello.gxapp
    
    # Run locally (QEMU for non-native)
    gxbuild run hello.gxapp

PRIORITY 2: UNIVERSAL BINARY SYSTEM
================================================================================
Status: HIGH PRIORITY
Phase: 8a, 8c, 8d
Dependencies: Priority 1 (partial)
Est. Duration: 8-10 weeks

The signature feature of guideXOS: single application packages that run on any
supported architecture.

DELIVERABLES:
-------------

2.1 Architecture Detection (Phase 8a)
    CpuArchitecture enum with all supported architectures
    ArchitectureDetector class for runtime detection
    CPU feature detection (SSE, AVX, NEON, etc.)
    
    API:
    CpuArchitecture arch = ArchitectureDetector::get();
    const CpuInfo& info = ArchitectureDetector::info();

2.2 GXAPP Container Format (Phase 8c)
    File Extension: .gxapp
    Container: ZIP archive
    
    Structure:
    myapp.gxapp
    ??? GXAPP              # Magic identifier
    ??? metadata.json      # Application metadata
    ??? signature.sig      # Optional Ed25519 signature
    ??? bin/
        ??? x86/app.elf
        ??? amd64/app.elf
        ??? riscv64/app.elf
    
    API:
    GXAppContainer* pkg = GXAppContainer::open("myapp.gxapp");
    uint8_t* binary = pkg->extract_binary(CpuArchitecture::AMD64, &size);

2.3 Universal Application Loader (Phase 8d)
    Combines architecture detection with container loading
    Automatic selection of correct binary
    Graceful error handling for unsupported architectures
    
    API:
    LoadResult result = UniversalAppLoader::run("calculator.gxapp");
    if (!result.ok()) {
        printf("Error: %s\n", result.error_message);
    }

2.4 ELF Loader Enhancement
    - Extend bootloader ELF loader for userspace context
    - Support dynamic relocations
    - Handle argc/argv/envp setup
    - Memory protection (RX for code, RW for data)

System for distributing and installing guideXOS applications.

DELIVERABLES:

4.1 Package Manager CLI (gxpkg)
    gxpkg install myapp.gxapp       # Install from file
    gxpkg install myapp             # Install from repository
    gxpkg remove myapp              # Uninstall
    gxpkg list                      # List installed
    gxpkg search <query>            # Search repository
    gxpkg update                    # Update package index

4.2 Package Repository (Simple HTTP)
    Static file server hosting:
    - packages/index.json           # Package index
    - packages/<name>/<version>.gxapp
    
    Index format:
    {
      "packages": [
        {
          "name": "calculator",
          "version": "1.0.0",
          "architectures": ["x86", "amd64", "riscv64"],
          "sha256": "...",
          "url": "packages/calculator/1.0.0.gxapp"
        }
      ]
    }

4.3 Installation Directory Structure
    /apps/
    ??? calculator/
    ?   ??? calculator.gxapp        # Original package
    ?   ??? metadata.json           # Extracted metadata
    ?   ??? current/                # Extracted current-arch binary

        ??? ...

PRIORITY 6: ABI TRANSLATION (FUTURE)
================================================================================
Status: LOW PRIORITY / FUTURE
Dependencies: All above
Est. Duration: TBD (research phase)

Long-term goal: Run binaries on architectures they weren't compiled for.

APPROACHES:
-----------
1. box86/box64 style - Translate x86/amd64 to other architectures
2. QEMU user-mode - Full emulation with JIT
3. Custom lightweight JIT - Architecture-specific translation

CONSIDERATIONS:
---------------
- Performance overhead
- Compatibility coverage
- Maintenance burden
- May not be worth it if native compilation is easy enough

DECISION: Defer until Priorities 1-5 are complete. Revisit based on
developer feedback and real-world usage patterns.

================================================================================
BUILD SYSTEM DECISIONS
================================================================================

CURRENT: Makefiles (working well for kernel)

RECOMMENDATION:
- Keep Makefiles for kernel builds (no change)
- Use CMake for SDK and userspace tools (better cross-compilation)
- gxbuild internally uses CMake or direct compiler invocation

RATIONALE:
- CMake has excellent multi-target support
- Integrates well with IDEs
- Good CI/CD integration
- Can generate Makefiles, Ninja, etc.
