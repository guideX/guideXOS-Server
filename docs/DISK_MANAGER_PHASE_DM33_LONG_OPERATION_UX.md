## Job and progress model

`Fat32FormatJob` binds the operation kind, full format request and exact target/partition snapshot, operation lease/pin, logical geometry, start tick, scan offset/total, result, and cancellation/commit state. The job is statically embedded in Disk Manager; it is bounded and the deterministic size check confirms it is under 2 KiB. One active destructive operation is allowed by the existing exclusive lease and job state guard.

States are Idle, Scanning, ReadyToCommit, Completed, Failed, and Canceled. Each update reads one transfer bounded by the 1 MiB scan buffer and the transport's maximum transfer. Progress is derived from exact scanned logical sectors/bytes, clamped to total, and exposed as phase plus percent and verified amount. The UI presents a progress bar and textual status, and exposes Cancel only while the scan can stop safely. A distinct READY_TO_COMMIT state creates an observable cancellation boundary after the final scan transfer. Formatter commit disables cancellation and consumes the private one-use KnownZero token.

Cancellation is cooperative at a bounded I/O boundary. It invalidates any in-progress authorization, releases the held operation lease and target pin, and performs no formatter writes or publication Flush. Nonblank, read error, removal, and identity changes retain distinct service results. Closing/shutdown calls cancel; the active-close explanation and behavior need a real GUI run before acceptance.

#### Production lifecycle audit

The blank-media formatter is `Fat32FormatJob` in `kernel/core/include/kernel/fat32_formatter.h`, with `begin_fat32_format_job`, `step_fat32_format_job`, `cancel_fat32_format_job`, `finish_job_failure`, and `cancel_job_now` in `kernel/core/fat32_formatter.cpp`. `begin_fat32_format_job` copies the `Fat32FormatRequest` (including immutable `TargetIdentity` and `PartitionEntry`), acquires `StorageOperationLease`, pins the exact block registration, validates the partition, then enters `FAT32_FORMAT_JOB_SCANNING`. One `step_fat32_format_job` admits at most one bounded synchronous sector read. Full coverage publishes the private `s_jobBlankToken` for that target, partition, geometry and lease owner, and changes state to `FAT32_FORMAT_JOB_READY_TO_COMMIT`. A later step rechecks ownership, token and target identity, consumes the token, sets `commitStarted`, and calls the existing formatter publication path. Terminal states are `FAT32_FORMAT_JOB_COMPLETED`, `FAT32_FORMAT_JOB_FAILED`, and `FAT32_FORMAT_JOB_CANCELED`; there is no dedicated `Removed` enum. Removal is a failed job with a status such as `FAT32_FORMAT_REGISTRY_CHANGED`, `FAT32_FORMAT_DEVICE_MISSING`, or `FAT32_FORMAT_READ_UNAVAILABLE`, depending on when and how it is observed.

USB port polling in `kernel/core/usb.cpp::poll` calls `usb_storage::release`. `kernel/core/usb_storage.cpp::release` marks the transport inactive/faulted and calls `block::mark_device_offline` for the matching registration. `kernel/core/block_device.cpp::mark_device_offline` marks a pinned registration forced-offline and advances registry generation; it leaves an offline tombstone while pins remain. Repeated invalidation of the same registration returns safely without repeating the state change. If a block read is already executing, the USB transfer is synchronous: `usb_storage::read_sectors` returns its transfer status, `block_read` maps removal to `BLOCK_ERR_NO_MEDIA`, and the per-I/O pin unwinds before the formatter sees the read result. UHCI's `wait_td` checks the monitored address during polling and has a bounded poll loop; there is no queued/asynchronous formatter read callback. If removal occurs between job steps, the next scheduled `step_fat32_format_job` sees the generation/identity invalidation before admitting another scan read. Thus no deferred callback can access a destroyed job, though a currently executing synchronous transfer must return first.

The job owns its request/result and persists as `DiskManagerApp::m_formatJob` in `kernel/core/kernel_apps.cpp`. `DiskManagerApp::update` copies job results and calls `completeFormatOperation` on terminal state. `closeInitializeDialog`, `shutdown`, and the destructor request cancellation while scanning or ready-to-commit. `release_storage_operation` / `complete_storage_operation_execution` in `kernel/core/disk_initialization.cpp` release the exclusive owner and unpin the captured registration; the last unpin removes an offline tombstone. Target revalidation includes registry generation and per-registration identity, so equal geometry cannot make a new registration satisfy an old target.

`KnownZero` is private to `fat32_formatter.cpp`. A partial scan has no token; cancellation and failed removal invalidate a token owned by that job; only complete scan coverage publishes it; commit consumes it after revalidation. Starting a new job clears prior private token state. `DiskManagerApp::scanDisks` drops the removed selection, while terminal handling updates the result dialog. The previous screenshot proves the progress widget disappeared, but the retained serial output contains no old-job terminal line; source alone cannot determine which UI path caused that exact screenshot. The explicit internal terminal state exists, but prior guest evidence did not show whether the specific B job reached it. This is an observability gap in the evidence path; the new host regression qualifies the synchronous removal seam, and the next guest run must confirm the real runtime path.
