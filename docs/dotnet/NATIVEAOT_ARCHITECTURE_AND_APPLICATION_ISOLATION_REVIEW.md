# NativeAOT application architecture and fault isolation

Independent architecture review · 20 November 2026 · AMD64 · branch `v1.1_DOTNET_SUPPORT` at `f9737a29271b457a38abd0368510b924cc331d1f`

## Decision

| Owner's question | Answer |
| --- | --- |
| Is the architecture sound for the goal? | **Partly.** The compiler, linked runtime and App Model form a credible implementation for a trusted suite of resident C# applications. The actual managed execution path lacks a kernel-enforced application lifetime. It cannot presently deliver failure isolation or independent executable lifetimes. Keep the working managed stack and change where independently deployed code runs. |
| What is the most dangerous assumption? | That managed entry will return to its native caller in a condition in which teardown can run. Entry borrows the kernel caller's stack and privilege with interrupts masked. A non-returning call can strand the desktop. The implemented fail-fast hook actually halts the executing CPU. |
| What prevents two independent real applications? | The first image occupies the only resident launcher/runtime slot. A different second image gets `Busy` even at a disjoint address. Removing that check would leave current-address-space mappings, one active callback identity, shared TLS machinery and no independently terminable owner. |
| What should happen next? | **Prove an AMD64 application can run in its own user address space and the kernel can retire it on exit, fault or timeout while an existing native application remains responsive in the same boot.** A small native fixture can exercise this exact prerequisite before paying the cost of a managed port. |

## A. From a compiled application to a returned callback

**Build and load.** The qualified build uses .NET 9.0.0 win-x64 NativeAOT, AOT-compiled C# and a linked Workstation runtime with selected guideXOS replacements. The build produces a PE and map, then a freestanding fixed-address AMD64 ELF retaining the code, data and metadata that the linked runtime expects. Inspection of the candidate ELF found seven load segments, base `0x100000000`, entry `0x1000F73A0`, and no dynamic section or relocations. There is no guest CLR installation, JIT, assembly discovery or general Windows loader in this path. Multiple source projects can be built into the composite. The C185/C186 SDK sample exercises that source-level boundary. It does not create a separately installed executable. [C106 architecture decision](NATIVEAOT_C106_MULTI_APPLICATION_ARCHITECTURE.md) · [C185](NATIVEAOT_C185_MANAGED_HOST_SERVICE_BOUNDARY.md) · [C186](NATIVEAOT_C186_MANAGED_HOST_CONTRACT_LIFECYCLE.md)

**Native admission.** Desktop `launch_managed_appmodel_record` passes a catalog record to `launchLogicalApplication`. An ordinary relaunch can focus an existing surface. A new activation reserves a native surface, assigns selector and generation, and supplies a scoped invocation context. `launchInternal` reads the VFS image, ordinarily `/system/apps/GXOSAPP.ELF`. `mapElf` validates the ELF envelope, executable entry, segment sizes and permissions, rejects occupied mappings, allocates tracked frames, copies/zero-fills the image and applies final page permissions. It maps supervisor pages in `address_space::current()`. `mapPage` accepts only the current tracked address space. Neither the selector nor the generation creates a process or changes privilege. [Desktop launch](../../kernel/core/desktop.cpp) · [Launcher and surfaces](../../kernel/core/nativeaot_application.cpp) · [Address space](../../kernel/core/address_space.cpp)

**Runtime entry.** The kernel builds startup/context records and calls the ELF entry as a Win64-ABI function. `GuideXosNativeAotApplicationEntry` installs the legacy PAL, Win64 PAL and GC platform hooks, calls the boolean-returning `RhInitialize`, installs the GS-based TLS bridge, prepares managed entry and calls the exported `ManagedMain`. The ready path reinstalls TLS and dispatches again. The failed-startup path is terminal for this image. The map binds `RhInitialize` to the guideXOS startup replacement, `RhRegisterOSModule` to the runtime's COFF CodeManager object, and `InitializeModules` to generated code in `HostLogProof.obj`. Reverse P/Invoke and array allocation use wrappers with renamed stock bodies. The existence of a familiar symbol alone does not identify its provider. [C entry wrapper](../../samples/managed/HostLogProof/c102_startup.c) · [Runtime platform and registration](../../tools/dotnet/runtime-pack/src/platform/guidexos_nativeaot_platform.cpp) · [R32 provider/attachment evidence](NATIVEAOT_R32_THREAD_CONSTRUCTION_AND_STACK_BOUNDS.md)

**Metadata and roots.** The platform derives module descriptors and managed/unboxing code ranges from linker markers and supplies a class-library callback table. `RhRegisterOSModule` installs address-based CodeManager dispatch. The pinned runtime supports a single registered managed code manager/range in a `RuntimeInstance`, alongside a list of type managers and OS-module metadata. A logical module descriptor, an App Model selector and an independently linked executable have different meanings. Generated `InitializeModules` creates type managers, builds GC-static base arrays, roots them through a normal GC handle and runs eager initializers. The local `g_guideXosNativeAotModulesInitialized` flag is set before the generated call. Its value alone cannot prove that initializers returned. R32/R36 supply stronger post-call evidence. One runtime in each private address space could reuse the same virtual addresses and unchanged single-manager semantics. This observation establishes feasibility of the ownership model, not that such a port exists. [Local registration](../../tools/dotnet/runtime-pack/src/platform/guidexos_nativeaot_platform.cpp) · [Pinned RuntimeInstance](https://github.com/dotnet/runtime/blob/9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3/src/coreclr/nativeaot/Runtime/RuntimeInstance.cpp) · [Pinned module initializer](https://github.com/dotnet/runtime/blob/9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3/src/coreclr/nativeaot/Common/src/Internal/Runtime/CompilerHelpers/StartupCodeHelpers.cs)

**Managed dispatch and callbacks.** `GuideXosApplicationRegistry.Dispatch` resolves a compiled descriptor. `GuideXosManagedApplicationLifetime.TryStartCore` invokes a typed factory, retains the managed object by selector/generation and dispatches its application methods. The Settings factory returns a C# object to C# code. The native side sees an integer result, window/instance identities and host calls. Input, actions, resize, close and activation re-enter the resident image. The native callback tables carry callable addresses, sizes, versions and capabilities. `activeSurfaceContext` checks the live context and identity. These checks support correct routing between cooperating apps. The table and activation arguments borrow invocation-lifetime storage. A worker cannot safely retain that storage or infer a current owner from a global after the call returns. [Registry and factory](../../samples/managed/HostLogProof/GuideXos/GuideXosApplication.cs) · [Lifetime pool](../../samples/managed/HostLogProof/GuideXos/GuideXosManagedApplicationC150Tests.cs) · [Managed ABI](../../samples/managed/HostLogProof/NativeAbi.cs) · [Native callbacks](../../kernel/core/nativeaot_application.cpp)

| Owner today | Contents and lifetime |
| --- | --- |
| Resident linked image | Generated code, type/GC/EH metadata, method tables, GC statics, allocator and GC handles, runtime instance and stock ThreadStore. Shared by the compiled selectors for the life of the image. |
| Kernel launcher/PAL | Image record and mapped-page ledger, VM reservations/frames, worker/event/FLS slots, GS backing and active callback identity. Host hook tables bridge the image's runtime to kernel services. Several stores have one global inventory. |
| Logical application | A strong managed entry in the lifetime pool, native managed surface, generation and associated window/action ownership. A close can release these without unloading the image. |
| One invocation | Native stack context, callback table and transient buffers, active selector and result. Ordinary return restores control. Nested synchronous calls save/restore selected context and can defer close until the outer activation returns. |

**Heap and execution model.** In the Workstation profile, `gcReserve/Commit/Decommit/Release` supply VM to the collector through tracked kernel regions. The runtime allocates and traces objects, consults type layout, enumerates static/handle roots and uses the CodeManager's method information and GC maps to enumerate live stack/register references at valid suspension points. `GCToEEInterface::SuspendEE/RestartEE` and the runtime ThreadStore coordinate collection. The kernel supplies accurate stack bounds and thread primitives. It does not infer managed roots by treating all memory words as pointers. An earlier image arena and a Workstation heap are different allocators. A manifest with `managedHeapBytes=0` in the latter profile means the old arena is absent. No per-selector heap, quota, relocation barrier between apps, or unloadable static set was found. A strong reference from a shared static can legally keep a closed app alive indefinitely. Managed references in untracked native storage cannot keep objects alive or follow compaction. Durable interop requires an explicitly owned handle or a copy, and a stable address requires the corresponding pinning/lifetime contract. [VM hooks](../../kernel/core/nativeaot_application.cpp) · [R21 profile and root experiment](NATIVEAOT_R21_REAL_SETTINGS_FACTORY_INTEGRATION.md) · [Pinned GC execution engine](https://github.com/dotnet/runtime/blob/9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3/src/coreclr/nativeaot/Runtime/gcenv.ee.cpp) · [Pinned ThreadStore](https://github.com/dotnet/runtime/blob/9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3/src/coreclr/nativeaot/Runtime/threadstore.cpp)

**Duplication.** guideXOS needs a native surface registry even when a managed object owns app behavior. The kernel owns windows and queue delivery, the GC owns object reachability. Likewise a kernel worker and the runtime's attached thread serve different purposes. The dangerous duplication is independent mutable state describing the same fact, particularly the two startup states and the generic/Win64 FLS stores below. Nothing examined justifies replacing the collector, adding a second kernel-side object tracer, or modifying upstream registration just to accept a second image.

## B. Ranked findings

### A managed failure can take the native desktop down with it

**Critical · confirmed mechanism**

`launchInternal`, `launchResident` and `invokeManagedWithHostMetadata` enter the image directly from kernel code with interrupts disabled. A PAL sleep can temporarily enable interrupts. An ordinary managed loop need never call it. The entry paths unconditionally re-enable interrupts on return. Nested native→managed calls therefore also need the caller’s prior interrupt state accounted for. Masking interrupts on one CPU supplies neither a system-wide lock nor a task boundary. `failFast` disables interrupts and halts in a loop on the executing CPU. In the examined AMD64 setup the kernel installs kernel code/data GDT entries, IRQ handlers and a page-fault handler. The expected-page-fault recovery hook is global and used by VM diagnostics. The ordinary unexpected-fault path halts. There is no managed-task trap frame to retire. Erroneous unsafe code or a runtime bug also executes with access to kernel-writable memory. The assessed consequence is loss of the caller, potential kernel corruption and UI liveness, without claiming every CPU stops or that R36 suffered such a failure.

**Validate/correct** with the user-task witness in E. For the trusted path, compare incoming and outgoing interrupt state on nested entry and restore the saved state where the caller requires it. Preserve the trusted composite lane while qualifying it. [Launcher, `failFast`](../../kernel/core/nativeaot_application.cpp) · [Interrupt setup](../../kernel/core/interrupts.cpp) · [AMD64 fault and exit handlers](../../kernel/arch/amd64/syscall.cpp)

### No independently owned lifetime for a second image

**Critical · confirmed limitation**

`g_application`, `g_pages`, `g_artifactBase` and the current page table describe a single mapping domain. `moduleFromPointer` returns the one image base. `launchResident` checks the existing path and rejects another. C104 used disjoint ranges `[0x100000000,0x10012E000)` and `[0x102000000,0x10212E000)`. That excluded simple address overlap as the reason for rejection. The linked runtime publishes pointers into the image, including metadata, statics, callbacks and worker targets. Unmapping or recycling its memory while any such pointer remains would create dangling references. There is no demonstrated safe unload sequence.

**Validate/correct** by establishing a disposable kernel owner first. Later qualify two private instances with the same fixed base, separate writable pages, different data and independent exits. Keep the existing `Busy` guard for the resident path. [C104](NATIVEAOT_C104_MULTIPLE_PRODUCTION_APPLICATIONS.md) · [Single-image design decision](NATIVEAOT_C106_MULTI_APPLICATION_ARCHITECTURE.md) · [Launcher](../../kernel/core/nativeaot_application.cpp) · [PAL worker retention](../../tools/dotnet/runtime-pack/src/platform/guidexos_nativeaot_pal_minwin_replacement.cpp)

### A failed startup can be reported reusable

**High · confirmed mismatch**

The image wrapper sets `kStartupFailed` on hook, `RhInitialize`, TLS or preparation failure and returns a stage-specific error. A later call sees a terminal state and returns `-104`. After the first entry returns, native `launchInternal` sets `Resident`, `runtimeInitialized=true` and `lifecycleReusable=true` before translating the return value into a launch status. The status can therefore say failure while the lifetime record says ready. Surface rollback does not fix the image state. This is a source-level contradiction. R36 did initialize.

**New hosted evidence.** I compiled the unchanged `c102_startup.c` entry with failure-injecting dependencies and ran eight fresh host processes, each calling the entry twice. All eight matched their expected returns and call counts. The first three hook failures returned `-102`, failed `RhInitialize` returned `-100`, TLS failed with `-103`, and failed preparation returned `-105`. Each of those six returned `-104` on the second call and never entered `ManagedMain`. A normal launch pair returned `0, 0`. Crucially, a successfully initialized runtime whose application returned the *same* `-100` subsequently returned `0` and called managed entry twice. The first integer return cannot distinguish those two cases. This executed the real C wrapper with hosted stand-ins, not the freestanding kernel or an actual failing runtime.

**Validate at the native launcher** by feeding these outcomes through the host state transition and inspecting the next launch report and surface ownership. **Smallest correction** communicate a distinct startup-completed result, publish reusable state only on completion, and quarantine a partially published image until its whole owner can be reclaimed safely. [Startup state machine](../../samples/managed/HostLogProof/c102_startup.c) · [Native return path](../../kernel/core/nativeaot_application.cpp)

### Thread identity and GC suspension do not extend to arbitrary managed workers

**High · confirmed mechanisms, strongly evidenced concurrency risk**

`installTls` writes the address of a common `g_tlsArea` into IA32_GS_BASE. The vector and first block are shared. `currentFlsContext` keys shadow values by native thread ID. `flsRelease` frees the generic index and clears its descriptor, while saved per-context values persist. A newly allocated Win64 index can see its previous value on the same thread. `flsDetach` does nothing. `workerEntry` attaches the native adapter, which by itself does not publish a stock runtime thread. R32 proves actual stock attachment on the bootstrap thread with a 16 KiB stack. `PalRegisterHijackCallback` records a callback and succeeds, but the linked `PalHijack` body does no work. Upstream suspension can request hijacking to bring another thread to a GC-safe state. The AMD64 switch handles CR3/FS, with no counterpart there for the managed GS backing and unfinished FPU/TSS work. A missed root, wrong thread static or suspension that never completes is plausible, with no two-mutator failure witnessed.

**Validate** slot release/reuse, thread exit and distinct thread sentinels first, then a bounded two-mutator collection with verified attach, stop and resume for each. **Correction** use one lifetime-aware TLS/FLS backing per thread/runtime and expose only suspension/worker capabilities the target can honor. A second managed mutator needs real safepoint coordination. [TLS, FLS and workers](../../kernel/core/nativeaot_application.cpp) · [PAL replacements](../../tools/dotnet/runtime-pack/src/platform/guidexos_nativeaot_pal_minwin_replacement.cpp) · [AMD64 switch](../../kernel/arch/amd64/context_switch.cpp) · [Pinned suspension/attachment](https://github.com/dotnet/runtime/blob/9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3/src/coreclr/nativeaot/Runtime/threadstore.cpp)

### Normal stack walking is qualified for specific frames. Exception recovery is open

**High · strongly evidenced coverage gap**

The stock COFF CodeManager maps IPs, interprets GC info, unwinds frames and enumerates managed exception clauses. The R20 `guideXosRtlVirtualUnwind` replacement advances real integer caller state for the qualified path. It ignores unwind flags and handler selection, consumes XMM-save entries without restoring those registers, and handles the frame-pointer operation only for the implemented register case. A read-only count of the exact PE's Exception Directory found 5,713 runtime-function records, 463 with chained unwind info and 36 with handler flags. Of 4,483 entries starting inside the map's managed-code envelope (RVAs `[0x1000,0xF1990)`), zero had either flag. These are records, not unique methods or observed invocations. Native helpers elsewhere in the image warrant attention. The image also links throw and catch-funclet machinery. Managed clause enumeration is separate from returning an OS handler. These facts do not establish that every catch fails, or even that a specific untested exception fails.

**Validate** nested catch/finally within managed code, stack/register integrity across an actual linked helper, safe outer-boundary translation, and an unhandled outcome in a disposable task. Compare the executed PCs and unwind forms with the exact PE. **Correction** implement or qualify the first unsupported form reached by a required path. [Local unwinder](../../tools/dotnet/runtime-pack/src/platform/guidexos_nativeaot_amd64_unwind_primitive.cpp) · [R20 proof](NATIVEAOT_C188R12R4R5R4R5R2R2R4R2R3R20_ITERATOR_ADVANCEMENT_ROOT_CAUSE.md) · [Pinned COFF CodeManager](https://github.com/dotnet/runtime/blob/9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3/src/coreclr/nativeaot/Runtime/windows/CoffNativeCodeManager.cpp) · [Microsoft x64 unwind format](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64)

### Close assumes application teardown returns

**High · confirmed cleanup ordering, hypothetical retention after failure**

Both `GuideXosManagedApplicationLifetime.Clear` overloads invoke virtual `OnTearingDown` before clearing the entry, without a `finally`. A throwing hook skips removal and leaves the strong entry present. Some factory paths catch errors, and the C185 external host bridge has guarded cleanup. Those protections do not cover every built-in dispatch. Native `onWindowClose` can dismantle surface state after a *returned* error, and `completeC162DeferredApplicationClose` depends on return from the active invocation. Forced abandonment cannot rely on a managed hook completing. C186 already qualified initialization/resize exceptions and adapter invalidation in its hosted bridge.

**Validate** returned error, thrown built-in teardown and repeated close separately, trace the generation, reclaim native resources and observe weak death after the owning frame is gone. **Correction** detach the exact old generation once even when user teardown throws, protect reentrant replacement generations, and provide kernel reclamation for owner resources independent of managed callbacks. ### Native and managed features can disagree in a hash-valid build

**High · confirmed for the qualified package**

R36's kernel required the C155 Notes handshake. The exact R23 builder selected C160 and omitted `-C155ManagedNotesSession`. The managed action succeeded through its older branch. Native session checks then failed before the App Model request. The map contains `ManagedSettingsCenter___ctor_0` at `0x100073ED0`. This establishes linkage only.

**Validate/correct** generate and compare required/provided features during packaging and reject this particular incompatible pair. When that user journey is under test again, require both selector-5 factory return and visible native window registration. The packaging correction is independently valuable but cannot establish fault isolation. ### Loader rollback and PAL memory protection have gaps

**Medium · confirmed control flow, unmeasured incidence**

In `mapElf` the newly allocated physical frame joins `g_pages` only after zeroing and a successful mapping. Failure at either intervening step releases previously recorded pages and leaves this frame outside the rollback ledger. `releaseMappedPages` also discards cleanup results. Separately, `virtualProtect` tests for a tracked address and nonzero length and reports an old RW protection without changing page tables. The ELF loader itself does apply real final permissions.

**Validate** inject a zero/map failure on the first and a later frame in a hosted accounting fixture, then check the owner count and page translation. For a requested protection change compare the full requested range and permissions before and after. **Correction** explicitly release the unrecorded frame, verify rollback results, and implement or reject unsupported protection requests accurately. The affected branches were inspected, not triggered on the guest. ### Similar records have different contracts

**Medium · confirmed branch divergence, hypothetical integration defect**

At the inspected local commits, `app_launch_target.h` is blob `2bcb1a44` here and `3cf9b28f` on main `bc2acf5a`, RX39 `3c4e18ed` and Tools13R1E `e7121065`. This branch inserts `ManagedNativeAotApp` before `ShellAction` and adds a managed path/selector. Numeric ordinals and native record layouts consequently differ. No evidence established that a persisted file transmits that C++ layout. RX39 also adds App Model activation/default-handler interfaces and native SDK callback tails such as `request_window_ex`, `file_read` and `present_frame`. Process implementation revisions differ. The native SDK and managed table already have different first callbacks at offset 8 (`get_api_version` versus `log`). Managed v4 has size 128 with snapshot/close/association at 104/112/120 and a 64-byte app context with activation/state/callback at 40/48/56. The PE-derived caller uses Win64 conventions even in its ELF wrapper.

**Validate/correct** compile both sets of producers/consumers against their declared ABI, assert layout and perform an actual callback round trip, exercise native and managed launch and resolve enum values by meaning at the integration seam. Preserve the separate tables. No cross-branch merge or ABI freeze is implied. **Low · confirmed maintenance concern**

**Validate/correct** record the selected source/profile, symbol-to-object mapping and guest hash together. An indexed pointer to the existing implementation is sufficient. ## C. Multi-application readiness and termination

| Scenario | Current outcome and confidence |
| --- | --- |
| Two trusted windows are open | Demonstrated on C181R1. Native surfaces retain distinct identity and generation while managed objects live in the same heap. Input can alternate. This is simultaneous residency with predominantly serialized execution. |
| Two distinct executables start | C104 directly observed rejection of the second and continued operation of the first. Current source retains the single-image guard. Neither successful independent residency nor parallel managed execution has been demonstrated. |
| App returns normally or is closed | Managed entry returning a status hands control back to the native caller. A successful launch can leave a live window. The close path dispatches teardown according to selector/profile, releases native window state and invalidates the surface generation. Notes slot release and reuse have direct guest evidence. Runtime/GC/worker mappings remain resident by design. |
| Entry rejects before or during initialization | Pre-entry errors can unwind native setup. On a returned managed-launch failure the surface can be closed/abandoned. After first entry, the reusable-state contradiction in B applies. A non-returning failure bypasses normal rollback. |
| App handles or lets an exception escape | Some factory and bridge code catches exceptions. Managed EH depends on linked tables, helpers and a correct stack walk. No retained evidence reviewed establishes a general recoverable unhandled-exception crossing of the native entry or survival of a sibling app after a fatal managed event. The installed PAL fail-fast path is terminal for its caller. |
| App hangs or receives a force-close | Closing a window, including the deferred Task Manager path, needs the native desktop to run. `create_init_process` records IDs, entry and stack. Kernel threads have owners, but the managed selector is not one of those task owners. `timer_tick` expires waits, `sys_exit` is a halt-loop stub, and the managed call has no independently scheduled user context to deschedule. Killing the borrowed native thread would endanger the host. [Process/threads](../../kernel/core/process.cpp) · [AMD64 syscall](../../kernel/arch/amd64/syscall.cpp) · [Managed close paths](../../kernel/core/nativeaot_application.cpp) |
| A closed app has outstanding roots or native resources | GC reclaims unreachable objects on its own schedule. A live static, delegate, handle or worker may still retain a graph. Native frames, VM slots, events, windows and queued callbacks require explicit ownership and revocation. No selector-scoped sweep or safe forced reclamation of the whole runtime was found. No measured production leak rate is available. |
| Two threads concurrently call into one runtime | Bootstrap attachment works on the qualified profile. Per-mutator TLS, stop/resume, stack roots and callback identity during overlap remain unqualified. Global current-context save/restore fits nested synchronous calls, not arbitrary concurrent invocations. |

The strongest positive result for the preview is real interaction across five named applications in an ordinary boot. The strongest negative result for independent apps is the deliberate A→B rejection, even at disjoint addresses. More window counts, larger descriptor arrays or another successful factory call cannot settle process isolation. Today's externally buildable app source can still be productive when incorporated into a trusted composite. A separately delivered binary needs a distinct kernel lifetime, runtime/heap identity and mediated access to host services. For an eventual private process, native host functions would be represented by user-side stubs. The kernel would validate the owner, handle generation and full buffer spans, then copy or otherwise explicitly share data across the boundary. Raw managed references and stack-local host callback tables cannot cross it.

## E. One next milestone — kernel-contained AMD64 application lifetime

Deliver **one disposable user task exercised by a small fixed-address native ELF fixture and one surviving native application**. This is the earliest experiment that can settle the highest-severity assumption independently of C155 packaging, GC metadata and exception handling. Correcting C155 would advance Settings. Extending the unwinder might qualify another managed stack. Neither lets the OS retire an application whose code cannot return. Removing the single-image guard would expose more shared state before the kernel can contain a failure.

Reuse the existing frame accounting, address-space primitives, native tasks, timers and App Model where their semantics fit. Supply the missing AMD64 user transition, kernel privilege stack, owner-specific mappings and bounded return path in this diagnostic lane. A user entry needs a private writable stack and image data, supervisor-only kernel mappings, interruptible execution and a kernel-owned context from which an expired or faulted task can be retired. The kernel must attribute traps using saved privilege and current task ownership and preserve its handling of genuine kernel faults. A tiny user exit/report interface is sufficient. The fixture and its owner ledger need only the resources exercised by this experiment. Keep the established trusted runtime as the preview path until a managed private task has separate qualification.
