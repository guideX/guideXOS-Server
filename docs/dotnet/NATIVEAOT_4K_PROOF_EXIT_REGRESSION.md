# NativeAOT 4 KiB Proof Exit Regression

## 1. Objective

This pass classified the reported `0xC0000419` exit from the bounded,
no-collection, 4 KiB repeated-allocation proof without changing the proven
Workstation GC first-refill loop, Workstation GC allocation behavior,
collection behavior, heap size, or expected allocation count.

The locked identities were NativeAOT source commit
`9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3`, ILCompiler/runtime pack `9.0.0`,
AMD64, and active PAL archive
`C617D95647A20862947B52A1301DF96FE9104E5A13F11BB0C016B8370DDE115F`.

## 3. Reason closure was blocked

The live 4 KiB rerun supplied for this pass was reported to exit through the
opaque value `0xC0000419` before managed diagnostics. That initial observation
is preserved in the existing first-refill report and was not rewritten.

The available preserved failing-run inputs did not contain a serial log,
process-return record, WER record, or runner transcript that contained the
value. Therefore the value could not be tied to a generating instruction or
source line. The current immutable artifact instead reproduced a normal pass
through every captured layer.

## 6. First origin of `0xC0000419`

No current layer generated the value. Two raw Server processes and three fresh
runner processes with immutable proof PE/ELF identities all returned
`0x00000000`. The preserved raw Server records include managed success, guest
return zero, normal `Exited` cleanup, and Server process return zero.

Windows Error Reporting contains a separate access-violation event for an
earlier Server process (`0xC0000005`, faulting module `gdi32full.dll`), but it
does not contain `0xC0000419`; it is preserved as context in
`exit-propagation/application-events.json` and is not treated as the reported
value's origin.

The exact missing invariant is a complete failing execution record captured at
the instant the value is first produced: process ID, raw `Process.ExitCode`,
WER record, final serial/Server marker, and the PowerShell native-command
return. Without that record, changing a runtime or runner contract would be
speculative.

## 8. Controlled-OOM result contract

The no-collection allocator calls `guideXosManagedAllocationCanFit` before
`new byte[256]`. When the next object does not fit, it records controlled OOM
and returns `0` to managed code. It does not call `RhpNewArray`, return a null
object, throw, request collection, expand the heap, or invoke fail-fast.

The managed proof reports the successful result and returns `0`. The observed
4 KiB report is:

```text
Managed allocations completed: 14; heap=4096; object=280; remaining=176;
pointerBeforeFailure=...; pointerAfterFailure=...; monotonicity=PASS;
nonOverlap=PASS; sampledIntegrity=PASS; zeroInit=PASS;
collectionEntered=0; heapExpansionOccurred=0; controlledOom=1
```

## 9. Server return propagation

`NativeElfExecutionResult::exitCode` is an `int32_t`. The executor assigns it
from the Win64 entry call, uses it for the cleanup state decision, records it
in `NativeAppProcessTable`, and reports it as `returnCode`, `exitCode`, and
`gxMainReturnCode`. The Server command path returns the executor result; it
does not reinterpret the managed `0` as an NTSTATUS or sign-extend a managed
status into a process exception.

The raw process capture under
`out/dotnet/gc-first-refill-closure/exit-propagation/raw-process/` confirms
both fresh Server processes returned signed `0`, unsigned `0`, and
`0x00000000`.

## 10. Process-teardown behavior

For each successful 4 KiB launch, the last managed/host marker precedes:

```text
Native ELF gx_main returned 0
lifecycle state after execution: Exited
cleanup attempted: true
state=Exited exitCode=0
```

The no-collection proof reaches controlled OOM, returns normally, and then
enters ordinary NativeAOT artifact cleanup. It does not use the Workstation GC
shutdown boundary. Runtime-level GC shutdown remains unsupported for the
first-refill QEMU experiment; process teardown is the supported boundary.

## 11. Runner behavior

The repeated-allocation wrapper passes the child runner's `$LASTEXITCODE`
through a nonzero check. The hostlog runner separately checks preflight,
positive Server-session exit, exact managed markers, and the intentionally
nonzero invalid-input failure probe. A failure-probe nonzero result is not
allowed to overwrite the positive proof result.

Three final fresh runner captures used the same runner hash
`4E5CEC37209A533F888FBFC4F0B93C20130F75009B0E63AF9E73526A2E1B1D10` and
returned `0x00000000`. Their saved stdout, stderr, and PowerShell transcript
hashes are in `corrected/final-4k/analysis.json`.

## 12. Historical successful evidence

The historical bounded proof remains the documented 14-allocation result with
heap 4096, object 280, remaining 176, controlled OOM, zero collections, zero
GC-backed allocations, and zero expansion. The current immutable artifact
matches that contract and identity. The initially observed `0xC0000419` is
retained as a separate unclassified live observation; it is not substituted
into or used to rewrite the historical PASS.

## 13. Root cause

No source-backed root cause for `0xC0000419` was established. The evidence
supports a precise classification: **the reported exit is a non-reproduced,
unbound execution result, not a demonstrated no-collection runtime regression
and not a demonstrated runner translation**. The available evidence is
insufficient to distinguish a transient host/launch event from a stale or
mismatched external invocation.

## 14. Correction

No source correction was applied. In particular, the successful first-refill
managed loop, Workstation GC allocator, no-collection capacity, expected count
14, collection behavior, runtime identity checks, and PE/ELF layout were not
changed. The only repository correction was adding the new local evidence root
`/out/dotnet/gc-first-refill-closure/` to `.gitignore`.

## 18. Remaining limitations

- The first producer of the externally reported `0xC0000419` is not proven.
- The failing serial/process/WER/PowerShell record needed to bind that value
  to a layer is absent from the available inputs.
- Runtime-level GC shutdown remains unsupported; process teardown is the
  tested boundary.
- The 4 KiB proof remains a hosted Server path, not a QEMU guest/parser path.
- No allocation after the first subsequent refill was attempted.

## 19. Decision outcome

**Closure Outcome B — the exit blocker is exact but correction remains a
separate pass.** The first-refill result remains technically valid, but the
milestone is not fully closed because the reported `0xC0000419` cannot be
assigned to a generating layer from the preserved evidence. No runtime or
runner correction is authorized on the basis of an unbound value.

Multiple subsequent refills, heap-segment transitions, new page commitments,
collection, and allocation beyond the established first-refill boundary are
not authorized.

## 20. Exact next experiment

After review, repeat only the bounded 4 KiB proof with the already preserved
PE/ELF and a process-launch capture that records, in one immutable run:

1. the exact Server PID and `Process.ExitCode`;
2. the final Server/managed marker and complete stdout/stderr;
3. the PowerShell `$LASTEXITCODE` before and after cleanup;
4. a timestamp-correlated Application Error/WER record if the process exits
   abnormally; and
5. the staged PE/ELF/runtime/kernel/ESP hashes.

Do not start multiple refills or segment-transition testing until that single
4 KiB event is either reproduced with a first generating layer or conclusively
shown to be an external harness/staging event.
