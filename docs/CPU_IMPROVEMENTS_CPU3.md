## Per-CPU foundation

`PerCpuState` owns a fixed roster of up to 128 descriptors using CPU2's capacity. The common AMD64 boot entry records its executing BSP at logical index 0 after selecting a valid boot method and before memory, display, or interrupt setup. It copies one CPU1 snapshot into kernel-owned storage. Other slots have no capability snapshot. The implementation uses static storage and has no frame or heap allocation. The default object's `.bss` is `0x880` bytes. [Roster interface](../kernel/arch/amd64/include/arch/per_cpu.h) · [Implementation](../kernel/arch/amd64/per_cpu.cpp) · [Boot call](../kernel/core/main.cpp)

| State or count | Meaning in CPU3 |
| --- | --- |
| Discovered | A complete, validated firmware record was copied. The descriptor retains the ACPI UID and the full APIC ID. The synthetic BSP has `Undiscovered` firmware state and can still have a CPUID-derived APIC ID. |
| Firmware-enabled | CPU2's MADT enabled bit is set. The other discovered states are firmware-disabled and firmware-online-capable under CPU2's MADT revision rule. |
| Initialized | The BSP descriptor and its capability snapshot are ready. Application-processor descriptors enter the roster as `Offline`. |
| Online | The processor has execution evidence from the existing AMD64 boot entry. The one supported transition is the already-executing BSP from `Initialized` to `Online`. |
| Offline count | The number of visible descriptors outside `Online`, including the BSP between its initialization and its online transition. It counts roster slots rather than all firmware records. |

With `CPU_INVENTORY_DIAGNOSTIC=1`, the boot adapter uses CPU2's checked BootInfo extension and reuses its identity matcher. The BSP moves to index 0 and the remaining records keep firmware order. Type 0 identifiers must fit their legacy widths, and each APIC identifier must be valid for its record type. Duplicate flags, conflicting flags, repeated APIC IDs or numeric ACPI UIDs, unsupported record types, and inconsistent counts reject the mapping as a whole before any firmware-backed slot is written. A missing, truncated, malformed, or uncorrelatable inventory leaves a complete synthetic BSP descriptor and zero secondary slots. A uniquely matched firmware-disabled BSP retains that firmware state while the executing kernel records it online. The default and legacy handoff paths use the BSP-only roster. [CPU2 identity contract](CPU_IMPROVEMENTS_CPU2.md#cpu1-identity-and-single-processor-operation)

Repeated initialization, online-before-initialization, repeated online transitions, and requests for any other index leave the roster intact. The diagnostic prints `[CPU3]` with mapping status and descriptor, online, and offline counts. The existing `[CPU2]` line uses the same snapshot and reports the executing count from CPU3. `boot_per_cpu_state()` exposes a read-only roster and stable indices that future scheduler and IRQ code can use to associate CPU-local state after qualifying their entry paths.

## Synchronization readiness

- The BSP is the sole roster writer and finishes publication during boot. IRQ, NMI, and AP paths have no roster consumers. CPU3 adds no atomics, spinlocks, barriers, or interrupt masking. The existing frame owner and address-space IRQ-save contracts cover local interrupts and provide no exclusion between CPUs.
- An AP rendezvous needs release publication of a fully constructed descriptor and acquire observation by the BSP and subsequent readers. Select fixed-width atomics and verify alignment, lock-free code generation, and GCC and MSVC behavior without relying on an unlinked runtime library. Keep each publication and its associated visibility and accounting under one contract. `volatile` alone supplies no such ordering.
- A future spinlock needs an explicit initialized state and ownership contract, acquire on success, and release on unlock. Code using a lock also taken by a local IRQ handler must save and mask local interrupts before acquiring it, release it before restoring the saved interrupt state, and independently exclude other CPUs. NMI or fault handlers need ownership rules that prevent waiting on an interrupted holder.
- Establish lock ordering from actual call paths across scheduler, frame owner, page tables, MMIO, and device state. Detect recursive acquisition and wrong-owner release in diagnostics. Keep waits for remote acknowledgements, reaping, serial output, and callbacks outside locks they may need. Test publication, contention, interrupt-state restoration with both incoming IF states, and two-CPU progress before wiring a primitive into shared kernel paths.
- Initial SMP work should identify per-CPU execution state and owners for global resources separately. CPU descriptors and future entry/scheduler state can be CPU-local. Physical-frame ownership, shared mappings, controller configuration, and system time still need a shared policy and synchronization of their mutations.

## Unsupported behavior and CPU2 dependency

Application-processor startup, INIT/SIPI and IPIs, LAPIC/x2APIC or IOAPIC enablement, APIC interrupt routing, hotplug, AP capability sampling, concurrent kernel execution, and preemption are outside CPU3. The existing PIC/PIT path, hardware entry state, Native ELF and CPL3 contracts, application ABI, and release policies remain the execution baseline. Counts describe CPU3's roster and give no estimate of hardware capacity or scheduler throughput.

CPU2's firmware memory-map capture and checked BootInfo handoff still require guest qualification with the matching loader. CPU3 also needs verification at the real boot boundary, including serial inventory, PIT heartbeat, keyboard and pointer input, desktop readiness, and clean synchronous Native ELF return. CPU3 used hosted and build evidence only. No guest was launched, and no QAC reservations or QEMU instances were controlled. [CPU2 guest disposition](CPU_IMPROVEMENTS_CPU2.md#guest-and-hardware-qualification)

## Recommended CPU4 milestone

First, qualify the CPU2 handoff and CPU3 roster in an explicitly authorized, isolated QAC guest lane using the matching loader and inventory-enabled kernel. Run a one-vCPU case and a multi-vCPU case. Capture the CPU1 APIC ID, CPU2 firmware counts and correlation, CPU3 logical BSP identity and one online processor, and evidence of PIT wakeups, keyboard and pointer delivery, desktop startup, and synchronous Native ELF return. Keep the candidate media and exact QAC ownership, serial, and exit evidence together.

Then extend read-only MADT inventory to I/O APICs and interrupt-source overrides, with fixtures for bounds, APIC IDs, duplicate and conflicting routes, polarity and trigger flags, and legacy IRQ0/1/12 mapping. Use that data to define vector allocation, destination width, controller and EOI ownership, and the CPUID/firmware/guest evidence needed for later per-CPU entry qualification. CPU4 should keep dispatch on the BSP through PIC/PIT while those contracts are verified.
