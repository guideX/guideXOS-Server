## Existing runtime and architecture plan

The existing pipeline is lexer → parser/AST → compiler/bytecode → one `RexxVM`. The VM dispatch loop owns the active chunk and `pc`; each `RexxInstruction` carries source-line metadata. Bytecode chunks own instruction arrays, copied literal constants, symbols, and parse metadata. Lexer tokens point into their source buffer, so the source must outlive lexing and parsing. AST nodes and compiler temporaries are released before execution.

Internal routine frames already hold caller/callee variable environments, argument vectors, stack and DO boundaries, numeric and ADDRESS state, condition state, and a return location. Variable generations and EXPOSE use the existing environment/alias machinery. Original labels live in the original program chunk. The VM has a shared dispatch budget and a shared numeric-work budget; condition traps and pending CALL ON events are held in VM/frame state. The evaluation stack and DO-frame array belong to the VM.

RX10 therefore adds one opcode and a bounded stack of dynamic continuations to that VM. It does not instantiate another VM or copy variables. A dynamic continuation records the parent chunk/PC, owned generated source and chunk, stack/DO boundaries, physical INTERPRET source line, and routine depth. Runtime translation uses the existing public lexer, parser, AST destructor, and compiler.

## Syntax and bytecode

`INTERPRET expression` is parsed as an ordinary clause and compiles the expression using existing expression rules, followed by `OP_INTERPRET`. At runtime the opcode consumes the evaluated value once, converts it through the standard REXX value-to-string path, and compiles those exact bytes. The source is not uppercased or sent to a shell.

The runtime path is:

1. Evaluate the expression once on the current VM stack.
2. Convert the value to a string with the VM's existing conversion rules.
3. Check source, nesting, aggregate-memory, and compilation-work limits.
4. Lex and parse the retained source buffer, rejecting labels.
5. Compile the AST into a normal `RexxBytecodeChunk`; free the AST on both success and failure.
6. Push a dynamic continuation and dispatch that chunk in the current VM.
7. On fragment completion, release its chunk and source, restore the parent chunk/PC and stack/DO boundary, and resume.

The existing parser handles semicolons and line breaks, complete IF/ELSE, DO, and SELECT structures, and the implied final clause terminator. Empty and whitespace-only strings compile to an empty fragment and return normally. Incomplete or malformed constructs produce a dynamic syntax diagnostic or a trapped SYNTAX condition.

## Ownership and execution contexts

Generated lexer tokens and parser nodes may point into the generated source. The source buffer is consequently owned by the active dynamic continuation and stays alive through fragment execution. The compiled chunk separately owns copied constants, symbols, and instruction/parse tables. A failed translation frees all partial AST/compiler state and leaves the currently active parent chunk and PC untouched.

Routine frames store both the return chunk and return PC. This allows a CALL originating in a dynamic fragment to return into that fragment without releasing its backing chunk. The continuation also records the routine depth at which it was created; RETURN, EXIT, SIGNAL, condition transfer, runtime failure, and normal completion unwind only the relevant dynamic contexts. CALL ON/SIGNAL ON condition target names are copied into the VM or routine frame, so registration does not point into a fragment that may be released.

All contexts are bounded arrays and are driven by the existing iterative VM dispatch loop. Nested INTERPRET is not native C recursion. On fragment completion, stack values above its saved boundary are cleared and local DO frames are discarded. The variable environment, live EXPOSE aliases, arguments, RC, RESULT, numeric settings, ADDRESS environment, and condition state remain the current VM/routine's state.

## Limits and shared budgets

| Resource | RX10 bound / behavior |
| --- | --- |
| One generated source | 65,536 bytes |
| INTERPRET nesting | 16 contexts |
| Aggregate live generated source | 262,144 bytes |
| Aggregate live generated bytecode storage | 4,194,304 bytes |
| Active generated instructions | 65,536 instructions |
| Runtime translation work | 8,388,608 charged units per VM execution |
| VM dispatches | Existing 1,000,000 instruction budget shared by original and generated bytecode |
| Numeric work | Existing per-execution numeric-work budget shared by all contexts |

Translation charges source bytes, parser nodes, and compiled instructions. Size additions and aggregate-limit checks are overflow-checked. Resource exhaustion, allocation failure, and VM/numeric budget exhaustion remain fatal safety errors; they are not converted into catchable SYNTAX conditions. Budgets are not reset at an INTERPRET boundary.

## Calls, returns, exits, and SIGNAL

An internal CALL from interpreted source uses the normal label lookup in the original root chunk and the normal current variable/routine context. Its frame captures the active dynamic chunk and continuation PC. RETURN resumes the interpreted fragment, applies normal RESULT handling, and releases a fragment only after no continuation can refer to it. INTERPRET inside PROCEDURE, PROCEDURE EXPOSE, and recursive routines uses their current generation/aliases and arguments. Numeric and ADDRESS context scope continues to follow existing routine-frame rules.

An interpreted RETURN returns from the active internal routine; an interpreted EXIT exits the whole script. Both unwind generated contexts safely. Generated labels are rejected during runtime translation. SIGNAL, including SIGNAL VALUE, resolves against the original program's labels; it may abandon active dynamic code and its pending control structures. Undefined labels keep the VM's existing controlled error behavior.

Each interpreted fragment is compiled independently, which enforces the classic implicit DO/END boundary: a complete local DO or SELECT must end in its fragment, and a dynamic LEAVE/ITERATE can act only on a repetitive DO within that generated fragment. Tests verify local LEAVE and verify that dynamic LEAVE/ITERATE do not escape to an enclosing caller loop. The parser/compiler's existing diagnostics are preserved for unsupported or malformed structures.

## Condition traps and source locations

NOVALUE and ordinary runtime conditions use the same active VM state and existing trap machinery. A parser/lexer/compiler syntax error discovered while translating generated source is classified as dynamic SYNTAX, reported with syntax RC 40, and offered to an enabled SIGNAL ON or CALL ON SYNTAX handler. Runtime errors raised by valid generated instructions use their normal condition rules. A permitted safe host-command failure in dynamic code continues through CALL ON ERROR, including DELAY and continuation after RETURN from the handler.

Generated instructions do not invent physical file line numbers. Their reported source line is the physical line containing the INTERPRET instruction that introduced the fragment. Thus SIGL and condition reports identify the source insertion point; dynamic diagnostics may include the generated-source parser message. Guest tests observed SIGL 16 for the original-label SIGNAL case, SIGL 3 for a NOVALUE trap, SIGL 6 for generated syntax, and SIGL 2 for a dynamic CALL ON ERROR.

The existing routine condition-context save/restore rules still apply to SIGNAL ON and CALL ON registrations. A transfer out of a fragment restores the proper parent or caller context and releases the abandoned fragment. Fatal resource failures are not catchable through condition traps.

## Known limitations and RX11 direction

- Regina was not installed, leaving 0 independent differential cases.
- SIGL maps generated source to the physical INTERPRET statement line; verify that detail against a reference interpreter when available.
- Runtime translation work uses a bounded unit budget, not a cycle-accurate measure of each lexer/parser operation.
- The implementation supports only the existing language and safe command callback surface; this phase adds no external routine loader, unrestricted ADDRESS dispatch, TRACE debugger, or new HALT/NOTREADY event source.

Recommended RX11 work: add an available Regina-based differential matrix for INTERPRET, SIGL, empty source, implied termination, and transfer boundaries; run ASan/UBSan on a host with supported runtimes; broaden fuzzed parser/allocator campaigns while keeping the current native QEMU smoke suite as the kernel regression gate.
