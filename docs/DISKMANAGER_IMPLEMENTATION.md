## Current behavior

The bare-metal Disk Manager enumerates registered block devices without adding a synthetic disk, parses normalized MBR/GPT state, and presents up to 128 validated partition entries plus bounded unallocated regions. The resizable view has a scrollable device pane, partition/unallocated list, proportional map, selected-object Properties, and Storage diagnostics. Disk, GPT/MBR partition, and gap selection follow stable identity across refresh. It offers **Initialize Disk...** only for raw eligible disks, defaults to GPT, and retains MBR as a compatibility choice. On a validated eligible unallocated region it exposes contextual **Create Partition...** for healthy GPT Basic Data or supported primary MBR FAT32-LBA partitions. The create flow supports integer-MiB or maximum sizing, a bounded GPT name, separate confirmation, and identity-based rescan. New partitions remain unformatted and unmounted.

For an eligible **Unformatted** or **Unknown filesystem** partition on a safe supported disk, the selected-partition action becomes **Format...**. FAT32 formatting accepts 512- or 4096-byte logical sectors and a fully zero-filled partition; other sector sizes remain unsupported. The dialog identifies the disk and partition, capacity, existing state, automatic FAT32 cluster size, and optional volume label. It requires explicit Format confirmation. On success Disk Manager rescans and selects the same partition by identity; Properties shows cached FAT32 metadata where available. Used/free space stays unknown. Formatting leaves the partition unmounted.

For a detected FAT32 partition, Disk Manager exposes an explicit **Mount...** action and **Unmount** for an existing mount. It proposes `/mnt/disk<device-index>-part<partition-number>` with deterministic numeric suffixes on collision. The mount dialog shows the disk, partition, FAT32 label, path, and read/write mode. FAT32 partition mounting supports matching 512- or 4096-byte logical-sector geometry and requires a valid, non-hybrid MBR or agreeing GPT table. The VFS mount record stores the parent registration ID, exact GPT unique GUID or MBR primary-entry tuple, bounds, view handle, path, filesystem type, and read-only state. Properties, partition rows, VFS mount enumeration, and File Explorer's Mounted drives pane expose the path. File Explorer can navigate to it through its existing VFS path handling.

For an eligible primary GPT or MBR partition, Disk Manager exposes **Delete Partition...** with a distinct confirmation naming the disk, partition number, size, filesystem/name when known, and mount state. Deletion removes the selected partition-table entry only; it does not wipe or securely erase former partition data. The user must unmount first. The dialog explains that the partition becomes inaccessible through normal mounting. Success refreshes the table and selects the resulting unallocated region by identity.

For an eligible parent-disk row, Disk Manager exposes a separate **Erase Entire Disk** action. It binds confirmation to the exact device registration, geometry, and stable serial, requires the user to type `ERASE <SERIAL>`, and requires a separate final activation. The operation writes bounded zero batches across every addressable sector, reports actual progress, and offers **Stop Erase** while Running. Stop uses the normal widget dispatcher and cooperative job path; the terminal result is shown only after required Flush and operation-ownership release. A stopped erase may leave partial data destruction and is not secure erase or sanitization.

## Blank-media scan and FAT32 formatter (DM23)

Formatting an eligible unformatted or unknown partition first verifies every partition sector is zero. The shared block request uses a fixed aligned 1 MiB static scan buffer, capped by the device's advertised `maxTransferBytes` and rounded down to complete logical sectors. The formatter accounts for every sector exactly once in increasing LBA order; the final partial batch is limited to the exact remaining range. The eight-byte-group zero test exits on the first nonzero data and reports its relative LBA and byte offset. Read failure, target loss, or nonzero data aborts before formatter writes.

The scan holds the exact storage-operation lease and registration pin. It checks lease and target identity for every read, then revalidates registration, partition identity and bounds, mount/boot state, write/persistence capabilities, and lease immediately after scan and before metadata I/O. A private one-use token binds verified coverage to that exact target, partition, geometry, and operation owner. The formatter consumes it once. DM22 metadata-sector zero rechecks and its 64-byte maximum rollback remain in place. The read-only probe and later confirmed format are separate calls, so Disk Manager scans twice across that interaction; one actual format transaction scans once.

USB advertises a 1 MiB common read cap, producing one READ(10)/(16) plus one CSW per full batch. The 1 MiB UHCI data phase has 16,385 TDs (64-byte maximum packets) across bounded 64-entry QH batches. Reads require exact expected bytes, zero residue, valid CSW, and endpoint toggles. AHCI advertises 128 KiB; NVMe advertises 128 KiB but remains read-only without proven write and Flush callbacks. ATA has no smaller common cap and issues one PIO command per sector within each shared read.

DM23 reports scan bytes, elapsed PIT ticks, MiB/s, request count and range, current absolute/relative LBA, and percentage in the operation result and proof serial output. The Disk Manager stays synchronous: there is no repaintable GUI progress or cancellation path during the scan, and the window may not respond until completion. The 862-check storage suite covers whole-volume coverage, final partial reads, nonzero/failure cases, replacement identity, mounts, token validity, and no-write-before-full-scan. See the [DM23 report](DISK_MANAGER_PHASE_DM23_BLANK_MEDIA_SCAN_SCALABILITY.md) for run evidence.

The hosted Windows viewer labels attached `.img` files as images and does not enumerate host physical disks. It previews validated 512-byte MBR ranges only; it does not parse GPT or classify remaining image space as unallocated. Image-backed RAM disks are read-only and volatile. Its current window remains fixed at 920×560. Host-image partition mounting is not supported.

When a USB parent disappears, UHCI root-port connection state and the connection-change latch are checked during active TD waits and BOT/block operations. The exact registration is marked offline before reuse, trusted Sync Cache state is revoked, and no new BOT command or destructive operation can start for that incarnation. Partition views reject I/O against a stale parent incarnation. VFS returns distinct removed, not-ready, timeout, unsupported, and I/O errors. Existing file and directory handles fail safely and can close; they keep unmount busy until closed. Once handles close, a stale mount can be explicitly cleaned up. Disk Manager Refresh/F5 clears stale selection and shows unavailable mounts; File Explorer checks stale mount backing before navigation and returns removal errors rather than redirecting to replacement media. Directory I/O errors remain distinct from EOF. Refresh remains manual because there is no block-registry notification mechanism. No safe-to-remove or eject action is presented.

For direct PIIX3 UHCI root-port devices, real QEMU hot-unplug/reinsert is proven while mounted (including open file and directory handles), during VFS write and multi-TD BOT data-out, and during Sync Cache before a valid CSW. Same-media and same-port different-media replacement receive new registration identities; old endpoints and handles remain stale. QEMU hub paths remain unsupported. USB serial/WWID boot identity can remain `Unknown` when no serial descriptor is available, while in-memory registration safety still uses fresh incarnation identity. See the DM14 report for exact stages and evidence.

Initialization creates an empty partition table and remains limited to confidently raw disks. DM6 partition creation writes only the selected table entry and required GPT checksums. DM7 writes FAT32 filesystem metadata only inside the selected partition; it does not modify the partition table or wipe all data clusters. DM8 mounts only after explicit user action and never formats or repairs on mount failure. DM25 removes one exact partition entry but does not erase its data. DM29–DM30 repairs only a missing or invalid GPT redundancy copy from its one valid peer; it does not resize, move, merge, convert, or otherwise edit a partition. Hosted `.img` viewing remains read-only.

## Destructive operation safety

Initialization, partition creation, FAT32 formatting/reformatting, deletion, and GPT repair use the shared exclusive storage-operation lease and target pinning. Each service keeps the lease through identity and registry-generation revalidation, writes, Flush, read-back verification, rescan, and cleanup. Operations with rollback snapshot their bounded metadata; GPT redundancy repair instead preserves its valid source and retries forward. Target registrations cannot be rebound while pinned. Forced removal marks the registration offline and prevents slot reuse until the pin is released. Registration IDs are monotonic and non-reused, and generation saturates instead of wrapping.

Destructive operations require current target identity and registry generation, valid geometry, read/write capability, trusted persistence, successful required Flush, unmounted/non-root state, definitely non-boot provenance, and the exclusive lease. Initialization accepts confidently raw metadata. Creation recomputes unallocated regions and derives a bounded partition entry. Formatting reparses the current table, matches the exact selected GPT GUID or MBR identity tuple, verifies its range and non-overlap, rejects mounted/root/boot-protected targets, and scans the entire partition. Delete reparses before and after confirmation, matches the selected partition identity, and changes only table metadata. GPT repair has its own authority and copy-state gates and never changes the valid source. Mounted partition views count as mounted parent disks for disk-wide operations. Only all-zero media is eligible for blank FAT32 format; recognized filesystems, unreadable media, and unknown nonzero data fail closed. Quick Reformat is a separate FAT32 operation, and there is no force-format or secure-erase option.

## Delete Partition transaction (DM25)

The delete service holds the shared exclusive storage-operation lease and pins the exact registration/incarnation through confirmation, execution, verification, rescan, and cleanup. Preparation reparses the authoritative table, checks partition identity and geometry, storage write/Flush capability, root/mount state, and boot provenance, then retains a bounded plan. After explicit confirmation it revalidates the target, parser state/fingerprint, mount/root/boot state, and metadata snapshot before mutation. GPT identity includes registration/incarnation, entry index, unique GUID, range, and parser/header/array fingerprints. MBR identity includes registration/incarnation, slot, type, start LBA, sector count, and table/disk-signature fingerprint. A stale selection is rejected; Disk Manager refreshes and requires reselection.

GPT deletion clears exactly the chosen entry bytes and recalculates both array CRCs and header CRCs. Other entries are not renumbered. The service snapshots only the selected entry's containing logical-sector span in both arrays plus the primary and backup header sectors. A selected entry fits within one array sector on supported 512-byte and 4Kn devices. Write order is: pre-write Flush and media recheck; backup array sector(s), backup header, Flush and copy verification; primary array sector(s), primary header, Flush and full two-copy verification; parser rescan and gap reconstruction. A GPT deletion therefore writes four metadata sectors. MBR deletion snapshots LBA0, clears only the selected 16-byte primary entry, writes the full logical LBA0 while preserving its other bytes and signature, Flushes, verifies, reparses, and reconstructs gaps. Extended/logical and hybrid MBR remain unsupported.

On a write, Flush, read-back, or rescan failure, rollback restores only snapshotted GPT array/header sectors or the saved MBR LBA0 sector. Rollback is allowed only while the original registration/incarnation, geometry, lease, and metadata identity remain valid; it then Flushes and verifies restoration. Removal or replacement produces an uncertain result and no rollback write is issued to replacement media. The delete path never writes the former filesystem/data range. Deleting and then creating a partition over the same range does not make its contents blank: the existing FAT32 formatter will reject those contents during its required zero scan.

Initialization, creation, and formatting attempt bounded restoration after write, flush, or verification failure. FAT32 formatting retains at most eight fixed-size rollback records (64 bytes maximum); each record stores a relative sector and its verified prior state. The full-partition zero scan remains mandatory, and every planned metadata sector is rechecked as zero before writes. A failure restores only those recorded sectors and rereads them. If target, lease, or partition identity cannot be revalidated, formatting stops and reports uncertain state rather than writing through an unverified partition mapping.

## GPT redundancy repair (DM29–DM30)

Repair is an explicit Disk Manager action with a second confirmation. The parser compares the complete primary and backup entry arrays after checking both copies independently. It preserves read-only partition inspection from the sole valid copy; conflict and no-authority cases do not expose a selected partition layout. Diagnostics show each copy state, redundancy state, protective-MBR status, and a specific repair blocker. Healthy, conflicting, and unrecoverable GPT do not offer a write action.

Preparation acquires the exclusive pinned storage lease and records the exact target, source GPT fingerprint, copy direction, usable range, disk GUID, and entry geometry. The confirmation names the target, capacity, logical sector size, damaged side, authority, fingerprint, partition count, and direction. Execution repeats the diagnosis and checks the registration, geometry, generation, operation owner, boot/mount policy, and source fingerprint after confirmation.

The repair writes only the damaged side: trusted pre-write Flush; complete padded entry array; byte-for-byte array verification; reconstructed location-dependent header written last; trusted post-write Flush; byte-for-byte verification of both copies, protective MBR, and the unchanged partition identity list; then ordinary parser rescan. The valid authoritative side is never rewritten. Repair is forward-only, not rollback-based: an interrupted damaged side remains eligible for a newly confirmed retry. Logical-sector size is limited to supported 512-byte and 4096-byte devices. All volumes must be unmounted. Root backing, boot backing, unknown boot provenance, read-only media, untrusted Flush, unreadable media, unsupported/bounds-invalid metadata, device-size mismatch, and both-invalid/conflicting tables fail closed.

The current-source deterministic suite covers both directions, bad signatures and CRCs, active and unused array bytes, split-brain arrays with valid CRCs, header-last ordering, two Flushes, interruptions/retry, stale source state, replacement media, mounted policy, boot provenance, read-only NVMe, and 4Kn. DM30 adds explicit three-entry 512-byte/4Kn QEMU fixtures and runtime write-range verification. Each runtime direction rewrites only the damaged array and header (33 sectors/16,896 bytes at 512 bytes; five sectors/20,480 bytes at 4Kn), performs two Flushes, leaves the authoritative copy, full LBA0/PMBR, nine data canaries and gap map unchanged, and passes cold restart plus independent whole-image verification. `scripts/verify-dm29-gpt.py` verifies CRCs, PMBR hash, normalized equality, partition identities, and exact changed LBA ranges. Cancellation tests prove zero writes and zero Flushes; source/model tests prove the Repair action gates. The actual graphical confirmation click-through remains unqualified. See the [DM29 design report](DISK_MANAGER_PHASE_DM29_GPT_REPAIR.md) and [DM30 qualification report](DISK_MANAGER_PHASE_DM30_OPERATIONAL_POLISH.md).

On degraded GPT, Initialize Disk remains unavailable because initialization accepts raw disks only. Create and Delete return a degraded-table blocker; FAT32 Format and Quick Reformat require a healthy pair; and VFS Mount accepts valid MBR or healthy agreeing GPT only. Repair is explicit and allowed only for one valid authority and a repairable peer when media is writable/durable, required Flush is trusted, partitions are unmounted, the disk is not root backing, and boot provenance is definitely not the target. No other operation silently repairs GPT.

## FAT compatibility and geometry

The existing FAT driver recognizes FAT16, FAT32, and exFAT for its existing direct-mount paths. DM8 adds an abstract block endpoint to FAT sector I/O. A partition endpoint exposes local sector 0 at the partition boot sector and bounds each request to the partition. The old MBR primary-partition compatibility probe also uses this bounded endpoint and records its identity. Explicit partition mounting advertises FAT32 only when the BPB sector size matches a supported 512- or 4096-byte device; FAT16, exFAT, ext, and UFS partition mounts remain restricted. The formatter supports 512- and 4096-byte sectors, power-of-two sectors-per-cluster with clusters no larger than 32 KiB, 65,525 through 0x0FFFFFEE data clusters, and BPB TotSec32 volumes through UINT32_MAX logical sectors (byte capacity depends on sector size). That is the formatter's representable geometry, not a claim that every transport or VFS operation has been tested at the maximum. The FAT32 BPB parser validates the same cluster-byte, cluster-count, root-cluster, volume-bound, and FAT-capacity constraints. FAT entries are read and updated on demand; the driver does not cache a whole FAT in memory. A valid FSInfo next-free value is used only as an allocation hint after the sector pointer and signatures pass checks; free-count values are ignored. FAT writes mirror to all copies and preserve the reserved high nibble. DM22 initializes only the first sector of each FAT, FSInfo sectors 1 and 7, backup boot sector 6, an optional root-label sector, and the primary boot sector last.

FAT32 formatting follows the standard 65,525-cluster minimum and reserves cluster IDs through 0x0FFFFFEF, allowing up to 0x0FFFFFEE data clusters. Sectors per cluster are selected deterministically from power-of-two values allowed by sector geometry, preferring the largest cluster size no greater than 32 KiB that leaves a valid FAT32 cluster count. BPB total sectors must fit 32 bits. Rollback memory is fixed-size and does not constrain FAT capacity. The formatter accepts large FAT32 partitions on 512- and 4096-byte-sector devices while retaining a full-partition zero scan; it does not zero or read back every FAT sector because untouched metadata was proven zero before writing. Its record array is capped at eight 8-byte entries (64 bytes total); current metadata consumes 48 bytes without a label and 56 bytes with one. Volume labels are padded to 11 FAT characters, may be blank, and remain independent of GPT partition names. Production volume IDs come from VirtIO RNG and must be nonzero; only storage tests can inject deterministic IDs.

## Boot provenance and transport capability

UEFI BootInfo v3 carries a bounded copy of the firmware loader source's Device Path plus resolved PCI segment/BDF where available. Legacy v2 or invalid metadata becomes `Unknown`. The kernel can match exact PCI plus NVMe namespace, supported legacy ATAPI channel/target, a direct USB storage path using controller BDF/root port/interface/optional class identity/LUN, or a direct SATA path using AHCI-controller BDF/port with PM `0xFFFF` and LUN zero. A match protects the entire parent disk, including when firmware names one partition. Different authoritative endpoints may be classified `DefinitelyNotBoot`; missing or unsupported identity stays `Unknown` and fails closed. USB WWID paths remain unknown because the USB core does not retain the serial string descriptor; VID/PID alone is insufficient. SATA port-multiplier and incomplete paths remain unknown with the current direct-port AHCI profile.

ATA PIO can satisfy boot provenance for supported legacy IDE/ATAPI paths and may pass destructive preflight when valid IDENTIFY flush support is present and all other safety gates pass. Standard-port fallback and unsupported ATA identity remain `Unknown`. AHCI registers direct SATA disks as `BDEV_AHCI` after IDENTIFY validates geometry and identity. It uses one polling command slot, bounded PRDT-backed DMA, shared reads/writes, and IDENTIFY-advertised ATA Flush commands; a QEMU ICH9 AHCI controller completed the full shared storage lifecycle and restart proof in DM15. AHCI uses UEFI SATA BDF/port provenance; the boot port is protected and the separately attached QEMU disk was authoritatively `DefinitelyNotBoot`. NCQ, port multipliers, ATAPI, non-AMD64 operation, and hotplug enumeration remain unsupported. See the [DM15 report](DISK_MANAGER_PHASE_DM15_AHCI_STORAGE.md) for implementation boundaries and evidence. NVMe uses serialized per-controller command ownership, strict completion matching, bounded one-page PRP transfers, validated command geometry, and a no-data Flush command. DM17's dense raw QEMU profile passed exact private write/read/restore checks, 100 Flush cycles, cold restart read-back, the shared write path, and five independent lifecycle images. The default build still registers NVMe as read-only: common write and Flush callbacks require explicit build switches, both disabled by default. See the [DM16 report](DISK_MANAGER_PHASE_DM16_NVME_DURABILITY.md) for the original failure and the [DM17 report](DISK_MANAGER_PHASE_DM17_NVME_DATA_INTEGRITY.md) for the reproduction, accepted configuration, traces, and limits. USB Mass Storage registers as BDEV_USB_MASS through production UHCI/BOT/SCSI in the common registry. Production WRITE(10)/(16), exact read-back, adjacent-sector preservation, and Sync Cache are implemented and covered by private-path and shared-block QEMU proof before the callback was enabled. The common USB write callback is installed only for a device that is not write protected; trusted Sync Cache is tracked separately. VFS mounts read/write and destructive operations are eligible only while persistence is trusted. A runtime failed or unsupported Sync Cache revokes trusted persistence until a successful retry. USB identity includes controller BDF, VID/PID, port, interface, LUN, SCSI model, and serial where available. SCSI INQUIRY RMB supplies removable state. See the DM13 report for full-lifecycle acceptance status and limitations. RAM and image-backed RAM disks are volatile and cannot satisfy durable destructive-operation policy.

## Persistence and geometry

Flush results distinguish supported successful flush, synchronous durable completion, unsupported or unknown semantics, and failure. Missing callbacks are not treated as durable. ATA uses E7h / EAh only when valid IDENTIFY word 83 bits advertise the corresponding command, then polls readiness and reports completion errors or timeouts. NVMe Flush uses the namespace-aware serialized I/O queue, exact command ownership, and completion validation. Its private durability and cold-restart gates passed in DM17. The default production build leaves the shared callback absent; the verified explicit profile may register it only together with the proven write callback.

The partition parser, initializer, and partition creator validate checked geometry for 512-byte and 4096-byte logical-sector devices. That does not imply every transport or filesystem supports 4Kn. FAT32 formatting and partition mounting now support matching 512-byte and 4096-byte logical-sector geometry; ext, UFS, FAT16, and exFAT remain outside 4Kn partition mounting.

## DM26 Quick Reformat
