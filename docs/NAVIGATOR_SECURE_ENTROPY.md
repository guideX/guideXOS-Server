# Navigator secure entropy (Phase 1)

Navigator’s bare-metal TLS randomness has one OS-level contract:

```text
secure hardware source -> kernel secure_random::fill() -> gxos_random_bytes()
    -> mbedtls_psa_external_get_random() -> TF-PSA-Crypto -> Mbed TLS -> HTTPS
```

The PSA external RNG option is enabled by `MBEDTLS_PSA_CRYPTO_EXTERNAL_RNG` in
`guidexos/crypto_config.h`. The callback is implemented in
`gxos_tls_foundation.cpp`; it reports success only after the secure provider
filled the complete request and sets the output length only on success.

## Supported sources

On x86 and x86-64, the kernel detects CPU capabilities with CPUID and tries
sources in this order for each request:

1. `RDSEED`, when CPUID reports it and bounded instruction retries succeed.
2. `RDRAND`, when CPUID reports it and bounded instruction retries succeed.
3. The existing transitional PCI `virtio-rng` driver, when the device is
   present and its bounded request succeeds.

`virtio-rng` currently supports the legacy/transitional PCI transport only.
Modern-only virtio-rng and non-x86 hardware are reported unsupported. The
provider returns failure when no source succeeds. It does not use a timer,
timestamp, TSC value, address, counter, MAC address, uninitialized memory,
deterministic seed, or any other weak substitute.

The shared `fill_from_word_source()` policy gives each RDSEED/RDRAND 32-bit
word at most eight attempts. A failed request clears the destination before
returning failure, so callers cannot mistake a partial prefix for successful
entropy. Zero-length requests succeed without requiring a source; a null
buffer with nonzero length fails.

## QEMU

The standard QEMU launchers include the canonical entropy arguments from
`scripts/qemu-secure-rng-args.ps1` / `.bat`:

```text
-object rng-builtin,id=rng0
-device virtio-rng-pci,rng=rng0,disable-modern=on,max-bytes=1024,period=1000
```

This exposes QEMU’s host-backed `rng-builtin` through the transitional PCI
device consumed by the existing driver. If the selected QEMU CPU exposes
RDSEED or RDRAND, the CPU source is preferred and virtio-rng remains a
legitimate fallback. To validate the virtio path specifically, use a QEMU CPU
configuration without those advertised CPU features while retaining the
arguments above.

The deterministic Navigator kernel smoke prints `rdseed_supported`,
`rdrand_supported`, `secure_rng_source`, `secure_rng_status`, and the existing
virtio-rng detection/status fields. It never prints generated bytes.

## Bare metal and failure behavior

On real x86/x86-64 hardware with a functioning and CPUID-advertised CPU RNG,
Navigator can use RDSEED or RDRAND without a QEMU device. If the CPU does not
advertise either instruction, or both instructions exhaust their bounded retry
budgets, a supported virtio-rng device is still required. No unsupported
device is silently treated as an entropy source.

When secure entropy is unavailable, the PSA callback returns
`PSA_ERROR_INSUFFICIENT_ENTROPY` for an unavailable provider or
`PSA_ERROR_HARDWARE_FAILURE` when a configured source fails during a request.
TLS setup and Navigator HTTPS therefore fail closed. Certificate validation,
hostname validation, trust-store policy, and plaintext-fallback policy are not
relaxed.

Useful bare-metal diagnostics include:

```text
[SECURE-RNG] provider initialized; rdseed=...; rdrand=...; virtio-rng=...; selected=...
[SECURE-RNG] CPU hardware RNG exhausted after bounded retries; request failed closed
[SECURE-RNG] no supported secure entropy source; request failed closed
[TLS-PSA] external RNG request failed; secure entropy unavailable
[TLS-PSA] external RNG callback registered; secure entropy status=ready
```

Existing DHCP and TCP legacy pseudo-random values are not part of this
provider and are never passed to PSA, Mbed TLS, or Navigator TLS.

## Phase 2 validation evidence (2026-08-27)

### Implemented

Phase 2 preserves the provider priority `RDSEED > RDRAND > existing
transitional virtio-rng > failure`. Priority describes candidates; each
request must be serviced successfully before that provider is recorded as the
source. A failing preferred provider is retried only within the existing
eight-attempt-per-32-bit-word budget, then the next legitimate candidate is
tried once. Counters for instruction retry failures, provider fallbacks, fill
requests, and fill failures saturate rather than wrap. Failed fills clear the
complete destination. No weak entropy fallback was added.

Bounded serial diagnostics now report CPU feature support, virtio detection
and readiness, selected source, provider status, fill/failure counts, retry
failures, provider fallbacks, PSA request/success/failure counts, and the last
PSA result. They never report generated bytes. The PSA callback records and
propagates invalid arguments, insufficient entropy, and hardware failures;
output length remains zero unless the complete secure request succeeds.

### Host-tested

The secure-random contract test passed for CPUID interpretation, provider
priority, transient and exhausted bounded retries, full output clearing,
invalid arguments, zero-length requests, and the no-provider path. The
source contract smoke passed for the provider diagnostics and PSA error
propagation. URL resolution, resource scheduler, resource diagnostics,
Mbed TLS/TF-PSA profile verification, and the hosted Navigator smoke passed.

The hosted public HTTPS corpus also passed its authenticated TLS checks for
`https://example.com/`, `https://www.iana.org/domains/example`,
`https://news.ycombinator.com/`, and `https://www.wikipedia.org/`. The
observed hosted protocol was TLS 1.2. The IANA case intentionally stopped at
an insecure HTTP redirect; no plaintext fallback was permitted. This hosted
lane uses the Windows system RNG and is not bare-metal entropy evidence.

### QEMU-tested

QEMU 11.0.0 and the repository-local OVMF image were available. The canonical
virtio-rng configuration was:

```text
-object rng-builtin,id=rng0
-device virtio-rng-pci,rng=rng0,disable-modern=on,max-bytes=1024,period=1000
```

Sixteen fresh deterministic kernel smoke boots completed with the
transitional virtio-rng provider selected. QEMU did not advertise RDSEED or
RDRAND in those boots. The logs show repeated secure fills, PSA crypto
initialization, and the PSA external RNG callback reporting a successful
secure-source request. The local production-policy certificate-negative
scenario reached TLS and correctly failed certificate verification; it was a
negative validation case, not an authenticated public HTTPS success.

The focused public HTTPS pilot did not run because the local candidate CA
manifest was `production_ready=no`; the policy correctly kept public HTTPS
disabled. No QEMU authenticated public HTTPS result is claimed.

The fail-closed QEMU lane used the test-launcher-only
`-DisableSecureEntropy` switch, which adds `-cpu max,rdseed=off,rdrand=off`
and omits virtio-rng. It produced `selected=none (secure entropy unavailable)`,
two failed and cleared random reads, `rng_fail_closed=true`,
`tls_backend_status=RngCallbackUnavailable`, `tls_smoke.tls_status=RngUnavailable`,
and `plaintext_fallback=no`. DNS/TCP/TLS for the public probe remained
`not-attempted`. The ordinary smoke harness therefore returned FAIL by
design because it expects secure entropy; the security assertions passed.
The PSA callback's `PSA_ERROR_INSUFFICIENT_ENTROPY` mapping is covered by the
contract smoke and source path; this runtime lane is gated before invoking the
callback, so no PSA insufficient-entropy callback event was observed in that
boot.

### Physically bare-metal-tested

No physical bare-metal boot or HTTPS connection was performed in this
environment. Therefore there is no physical CPU/provider/boot count, and no
claim is made that Navigator has completed an authenticated HTTPS handshake
on physical AMD64 hardware. Certificate verification and hostname
verification remained enabled in all tested TLS paths; no `VERIFY_NONE`
equivalent was used.

### Known limitations and classification

The shipped virtio-rng implementation is limited to the existing
legacy/transitional PCI transport; modern-only virtio-rng is unsupported.
The i686-equivalent `ARCH=x86` build still fails on the pre-existing missing
freestanding `string.h` headers (and `ARCH=i686` is not a valid Makefile
target). It was not repaired in Phase 2. The practical Phase 2 result is
Outcome B: implementation and host/QEMU validation are sound, but physical
bare-metal HTTPS remains externally blocked.

## Tests and troubleshooting

The host contract test covers CPUID mask interpretation, successful word
assembly, transient retry then success, retry exhaustion, unsupported source,
zero-length handling, invalid arguments, and the no-fallback failure path:

```powershell
.\scripts\smoke-secure-random-contract.ps1
```

For a guest failure, first check the serial fields in this order:

1. `tls_prereq.rng_quality` must be `Secure`.
2. `tls_prereq.secure_rng_source` identifies RDSEED, RDRAND, or virtio-rng.
3. `tls_prereq.secure_rng_status` identifies unsupported, exhausted, or
   unavailable state.
4. If virtio is expected, confirm `virtio_rng_detected=yes`,
   `virtio_rng_status=success`, and that QEMU used both canonical arguments.
5. A PSA RNG failure must remain visible as a TLS setup/handshake failure; a
   run that continues with predictable bytes is a defect.

The host/unit contract test does not demonstrate a physical CPU or a physical
Navigator HTTPS handshake. Those require interactive bare-metal execution and
remain a follow-up validation item.
