### Intent and configuration trace

Classic-at-boot is intentional. The repository's theme plan repeatedly states that Classic is the compatibility default and Sci-Fi is opt-in (including sections 4F, 4H, 10A, and the release qualification notes). The Display Options Theme tab also labels Classic as the default and Sci-Fi as opt-in. The branch name and the presence of Sci-Fi assets do not change that product decision. No dedicated-v0.3-Sci-Fi boot-default requirement was found.

The production configuration chain is:

1. `ESP/desktop.cfg` is a tracked source configuration file; its `desktopThemeId=classic` value is deliberate. `build.ps1` stages the `ESP` tree as the boot volume and does not synthesize or replace this key. The wallpaper pack generator builds `ESP/ramdisk.img` separately and does not choose a theme.
2. The bare-metal settings loader in `kernel/core/desktop.cpp` reads `/desktop.cfg` after the boot volume is mounted. An absent/unreadable configuration, empty ID, or unrecognized ID resolves to Classic. Serial reports the normalized identifier as `[desktop] loaded desktop theme=<id> source=<source>`.
3. Canonical IDs are `classic` and `scifi`; the enum member is `DesktopThemeId::SciFi`, and `DesktopThemeIdToString` emits `scifi`. Parsing is case/spacing/separator insensitive for recognized theme tokens. Invalid values fall back to Classic.
4. The supported interactive selector is Display Options → Theme. Choosing a theme saves `desktopThemeId` through the existing display-options persistence path and publishes `MT_DesktopConfigReload`; the desktop reload handler synchronizes the current theme and redraws without a reboot. The preference persists for subsequent boots. Wallpaper preference remains global and is not changed by theme selection.

The earlier candidate's `desktop.cfg=classic` was therefore expected product behavior, not a packaging defect. The production build was not changed and no default was forced.
