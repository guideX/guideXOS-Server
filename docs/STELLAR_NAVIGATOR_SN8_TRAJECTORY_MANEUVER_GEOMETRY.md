# Stellar Navigator SN8 — Simulated Trajectories and Maneuver Geometry

SN8 adds a portable, idealized Sun-centered two-body propagator and a sampled trajectory / impulsive-maneuver view to the existing Stellar Navigator application. The result is a simulation feature, not a spacecraft navigation product.

## Scientific model

The relative spacecraft state is propagated using Newtonian point-mass gravity:

`a = -μ r / |r|³`

The spacecraft is treated as massless and the Sun is the only gravitating body. State position is in meters, velocity in meters per second, time in ET/TDB seconds past J2000, and μ in m³/s². The camera and map projection never feed back into the state.

The implementation uses universal variables in binary64. It brackets the universal anomaly, then uses safeguarded Newton steps with bisection fallback. Stumpff C/S functions use a series around zero, trigonometric expressions for positive arguments, and hyperbolic expressions for negative arguments. The root refinement is bounded to 100 iterations; bracketing is separately bounded to 100 steps. Convergence uses a scaled residual tolerance of `max(1e-13, sqrt(μ) * |Δt| * 5e-15)`. Non-finite values, a missing bracket, unsupported arguments, and iteration exhaustion return typed failures. No straight-line substitute is produced.

The propagator supports circular and general elliptic, near-parabolic, and hyperbolic conics within its numerical bounds. Near-parabolic classification is `|α r| ≤ 1e-10`, where `α = 2/r - v²/μ`. Supported input radius is 1 m through `1e16` m, speed is at most `1e6` m/s, and radial / zero-angular-momentum states are rejected. Each propagation interval is limited to 100 Julian years. Stumpff evaluation is bounded to `sqrt(z) ≤ 1e8` for positive z and `sqrt(-z) ≤ 300` for negative z. These are implementation limits, not accuracy claims outside the tested domain.

## Independent CSPICE verification

`StellarNavigator.Tests/sn8_propagation_reference.json` contains 200 deterministic `CSPICE_N0067 prop2b_c` results generated by `tools/sn8_make_propagation_reference.py` with host-side spiceypy. The fixture uses seed `20261018`, ET/TDB seconds, SI state units, and the same authenticated DE440 solar GM. Each of the four regimes has 50 cases: circular, elliptical, hyperbolic, and parabolic / near-parabolic. Cases vary initial states, orbital planes, propagation durations, and direction, and include forward and reverse propagation.

The managed runtime and tests do not require Python, spiceypy, or CSPICE. Recorded vector-error statistics over all 200 comparisons were:

| Quantity | Maximum absolute error | RMS absolute error | Maximum relative error | RMS relative error |
|---|---:|---:|---:|---:|
| Position | 0.0741838072 m (`sn8-176`) | 0.00829767394 m | `6.83416982e-14` | `6.66357080e-15` |
| Velocity | `5.22091946e-10` m/s (`sn8-148`) | `6.84371758e-11` m/s | `3.93963019e-14` | `5.72765823e-15` |

The test separately enforces relative error at most `2e-13`, position absolute error at most `0.01 m + scale × 2e-13`, and velocity absolute error at most `1e-7 m/s + scale × 2e-13`. It also checks circular-orbit half / full-period behavior, zero-interval identity, reverse propagation, and deterministic output.

Independent two-body invariants are tested during a three-year unpowered coast: relative specific-energy change is at most `2e-13`, and relative angular-momentum magnitude change is at most `2e-13`. Circular half-period and full-period checks bound position error to 0.02 m and velocity error to `2e-8 m/s`; reverse consistency is bounded to 0.05 m and `5e-8 m/s`. The independent CSPICE comparisons remain the main reference check. These results qualify the numerical implementation against the same mathematical model; they do not validate any simulated initial condition against flight observations.

## Demonstration scenario and limits

The editable demonstration is `SN8-DEMO`: a synthetic state at ET 0 with position `(149597870700, 0, 0) m` and velocity `(0, 29784.6918, 0) m/s` in Sun-relative J2000-aligned axes. Its central body and dynamical origin are the Sun (NAIF 10). The scenario allows at most 100 Julian years from its initial epoch. This is a deterministic teaching / visualization state, not an observed orbit or mission plan.

All successful simulated states are labeled `ApproximateOrSimulated`. If the requested UTC conversion is provisional under the inherited SN5 policy, the trajectory carries the conservative stale-time quality. Numerical agreement with CSPICE never promotes simulated spacecraft states to `ValidatedReference`.

## Maneuvers and timeline semantics

An impulse is an instantaneous J2000 velocity delta: `v_after = v_before + Δv`; position is identical at the event epoch. Both pre- and post-impulse states are retained. The displayed state at an exact event ET uses post-impulse velocity, while the pre-impulse state remains selectable through maneuver details.

The timeline accepts at most eight events. IDs and ET epochs must be unique; ET must be finite, on or after the initial scenario epoch, and within its horizon. Δv must be finite, use J2000 components, and have magnitude at most 50,000 m/s. Events are sorted by ET and then ID for deterministic processing. Disabled events remain in the schedule and retain their requested Δv for inspection but produce no velocity jump or segment change. No frame transformation is inferred. These are simulated impulses, not thruster commands.

The GUI validates edits before requesting a scene rebuild. The previous valid scene stays displayed if validation or propagation fails. Accepted state changes are committed only when the matching generation completes; newer requests cancel earlier work, and closing the form cancels outstanding builds.

## Sampling and rendering

The scene samples a deterministic ET interval with 49 regular requests by default. Current ET, scenario initial ET when in range, and maneuver boundaries are inserted explicitly. Enabled impulses add pre- and post-event samples at the same position; samples are ordered by ET with the pre-state before the post-state. The final trajectory is capped at 512 retained samples, including boundaries. Requests outside the scenario horizon or that exceed the cap fail with diagnostics. A sampled polyline approximates a continuous conic; no chord-error bound is claimed.

The dynamics stay Sun-relative. For SSB rendering, the scene places each relative state using the DE440s Sun barycentric state at the same ET:

`r_spacecraft_SSB(t) = r_sun_DE440s(t) + r_spacecraft/Sun_two-body(t)`

Velocity is composed the same way. The requested map origin and existing frame services are then applied. This is an epoch-consistent visualization convention, not an N-body integration of the Sun / spacecraft system. Planet positions continue to come from the authenticated DE440s provider. Camera motion only changes presentation coordinates. Existing sampled geometric trails remain separate from the propagated spacecraft path.

## GUI controls

The Windows Forms host provides:

- SN8 trajectory and maneuver-marker visibility toggles.
- ET seconds (TDB), JD TDB, and existing UTC input modes, with the inherited strict / provisional time policy.
- Existing epoch stepping and playback, scientific origin, frame, map fit, reset, center, zoom, and pan controls.
- An editable Sun-relative initial epoch, position in meters, and velocity in km/s, plus a demonstration reset.
- A bounded maneuver editor for ET, Δv X/Y/Z in m/s, label, enabled state, add / update, and remove.
- Selection details for spacecraft, samples, and maneuvers, including units, distance / speed, event pre/post speed, model, provenance, quality, validity limits, and approximation notes.

The map uses the existing floating-origin double-precision projection. Maneuver markers can be selected and highlighted. GUI calculations run asynchronously and use generation IDs / cancellation to prevent stale scene results from replacing newer ones.

## Failure handling and dependencies

The portable model rejects invalid or non-finite μ and state input, degenerate radial motion, unsupported conic arguments, horizon violations, nonconvergence, invalid / duplicate / pre-initial maneuvers, invalid frames, and excessive samples. Scene construction reports unavailable DE440s epochs and authenticated orientation failures instead of drawing a fallback. Missing or corrupt solar GM disables SN8 trajectory controls; it does not substitute a hardcoded value.

The managed runtime depends on the existing portable astronomy / time / ephemeris libraries and local authenticated data assets. It has no CSPICE, Python, network-service, SQL, Windows Forms, graphics, or camera dependency in the propagator. Windows Forms remains only in the hosted GUI layer.

## Remaining guideXOS Server integration

SN8 keeps its dynamics and scene generation in portable .NET libraries and leaves guideXOS kernel sources unchanged. The remaining server work is to host these portable model / scene APIs in the intended guideXOS Server UI, connect its accepted time and ephemeris services to the request boundary, expose the scenario editor and selected-state detail surfaces in that host, and repeat the reference / bounds / quality checks in the server build and runtime environment. The Windows application is the secondary demonstration host, not a new standalone product architecture.

## Recommended SN9 scope

Use SN9 to establish a separately validated transfer-targeting milestone: first define the state / epoch / coordinate contract and solver fixtures, then implement a bounded Lambert boundary-value solver and expose its result explicitly as a transfer solution rather than as a direct propagation. Keep N-body propagation, patched conics, real telemetry, navigation estimation, and flight claims out of scope until independently specified and validated.
