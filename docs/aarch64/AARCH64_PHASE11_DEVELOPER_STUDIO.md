# AARCH64-11 — Developer Studio and resident multi-architecture compilation

Status: implemented and QEMU-validated on `AARCH64_SUPPORT`.

Phase 11 adds a bounded Developer Studio build path that executes inside the
ARM64 guideXOS guest. The kernel owns the compiler frontend, ARM64 and AMD64
byte emitters, ELF writer, project validation, VFS I/O, package publication,
and App Model refresh. The staged Developer Studio client is only the SDK
client that exercises that resident service; it does not invoke a host
compiler or a host process.

## Proof boundary

The proof is deliberately a bootstrap compiler, not a production C/C++
toolchain. It accepts exactly one function:

```c
int gx_main(void* ctx) {
    log(ctx, "bounded message");
    return 42;
}
```

The parameter type may also be `gx_app_context*`. Up to four sequential
`log(ctx, "...");` statements are accepted, followed by one signed 32-bit
integer return. String escapes are limited to `\\n`, `\\r`, `\\t`, `\\"`, and
`\\`. There are no declarations, expressions, locals, branches, loops,
includes, multiple translation units, relocations, symbol tables, dynamic
linking, or general C/C++ semantics in this milestone. Unsupported input is
rejected before publication.

The compiler reads and writes through the guest VFS. It does not call
PowerShell, LLVM, QEMU, a host filesystem path, or an external linker during
the guest build. The external build script only creates the bootable kernel,
stages the Developer Studio client, and supplies the initial AMD64 control
payload; the proof application's ARM64 and AMD64 siblings are regenerated by
the guest service from the saved source.

## Target and ABI contract

The compiler target model maps to the canonical App Model architecture
identity:

```text
CompilerTarget::Arm64 -> NativeArchitecture::ARM64 -> arm64 -> EM_AARCH64 (183)
CompilerTarget::Amd64 -> NativeArchitecture::AMD64 -> amd64 -> EM_X86_64 (62)
```

`Current` resolves through the common `CurrentNativeArchitecture()` boundary.
The service exposes these exact profiles:

```text
guidexos.arm64.baremetal.bootstrap.native
guidexos.amd64.baremetal.bootstrap.native
guidexos.current.baremetal.bootstrap.native
guidexos.multi.baremetal.bootstrap.native
```

The generated image is ELF64, little-endian, `ET_EXEC`, one deterministic
RX `PT_LOAD`, no `PT_INTERP`, no `PT_DYNAMIC`, no relocations, and no W+X
segment. ARM64 uses the existing loader base `0x50000000`; AMD64 uses the
bootstrap writer base `0x200000`. The guest validator checks the machine,
entry point, load bounds, alignment, executable entry, and exact emitted code
bytes before the image is accepted.

The ARM64 backend follows AAPCS64. `x0` is the incoming `gx_app_context*` and
the return value is produced in `w0`. For logging, `x19` preserves the context
across the indirect host call, `x16` loads `ctx->host->log`, `x1` receives a
literal address, and `blr x16` performs the call. The backend saves/restores
`x19` and `x30` with a 16-byte aligned stack frame. `ADR` range checks are
bounded to its signed 21-bit byte displacement.

The AMD64 backend emits the existing six-byte return-only function for the
legacy grammar and a Windows x64 ABI-compatible shadow-space sequence for
logging. It is emitted on ARM64 as a cross-target artifact; it is not executed
by the ARM64 guest.

## Build service and package update behavior

`BareMetalBuildService` accepts only the bounded NativeElf project contract:
`guidexos.project`, `app/app.json` (or package-root `app.json`), the canonical
project kind and ABI, safe relative source paths, an `/Apps/...` package root,
and the exact requested target profile. The service is single-job and bounded
by the compiler source, token, diagnostic, log-call, message, and ELF limits.

For a multi-target request it compiles ARM64 and AMD64 from the same VFS
source, validates both images, copies them to `build/bin/<arch>/app.elf`,
copies both to `bin/<arch>/app.elf`, and writes `app.json` last. A failed
source parse or target compile leaves the previously published package in
place. A successful rebuild changes the package generation and fresh payload
bytes. The service records deterministic `fnv1a64-<hex>` evidence in the
snapshot; the field names remain ABI-compatible with the older `artifactSha256`
names, but the guest value is explicitly not a cryptographic SHA-256.

The package resolver is refreshed after the Developer Studio build and before
the generated application is launched. The existing App Model exact-entry
policy then selects `bin/arm64/app.elf`; it never falls back to the staged or
generated AMD64 sibling on an ARM64 guest.

## In-OS proof sequence

The checked-in client is
`sdk/samples/phase11_developer_studio/main.cpp`. It edits
`/Apps/Phase11CrossArchApp/src/main.c`, requests the multi-target profile,
polls and releases the bounded build handle, and verifies:

1. build 1 generates both machine types and publishes the package;
2. invalid source is rejected while the old final package remains present;
3. build 2 changes the source and produces a changed artifact digest;
4. the kernel refreshes App Model discovery; and
5. the generated ARM64 payload logs its Developer Studio messages and returns
   `42` through the normal NativeElf runtime cleanup path.

The ARM64 proof does not require QMP or GUI automation because the compiler
scope is a serial log ABI. The desktop, framebuffer, input, scheduler, VFS,
NativeElf loader, App Model selection, and runtime cleanup still run through
the existing Phase 9/10 kernel path. The QEMU harness uses a fresh UEFI vars
file for each boot and rejects Phase 11 errors, wrong architecture, unexpected
IRQs, and exceptions.

## Build, boot, and regression commands

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-aarch64-phase11.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-aarch64-phase11.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-aarch64-phase11.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-compiler-arm64-host-test.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-compiler-bootstrap-host-test.ps1
```

`build-aarch64-phase11.ps1` first builds the ARM64 kernel with
`GXOS_AARCH64_PHASE11`, then compiles only the checked-in Developer Studio
client and a pre-boot AMD64 control payload. It intentionally does not stage
`Apps/Phase11CrossArchApp/bin/arm64/app.elf`; that file must appear only after
the guest compiler runs. `test-aarch64-phase11.ps1` repeats the boot with
three independent UEFI variable files and checks all application markers.

## Remaining work

The next compiler milestone is a real typed AST and object/linker pipeline,
with a versioned source language and a cryptographic digest implementation in
the guest ABI. It should retain the same package-generation invalidation,
exact architecture selection, no-fallback policy, and ELF defense-in-depth.
EL0 isolation, SMP execution, a general C/C++ frontend, multiple translation
units, relocations, and full AMD64 guideXOS boot remain outside AARCH64-11.
