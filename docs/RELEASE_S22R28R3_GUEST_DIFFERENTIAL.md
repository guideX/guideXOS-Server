## Staged sector-zero evidence

The Recovery2 FAT trace ISO did not record the three stage fingerprints needed to locate where the source-to-guest difference first appears. Candidate `S22R28R3R1-FP512` (source commit `d22debb09ca448e6f5e6145bab6dd1e07f0dad1d`) was therefore built offline from a copy of the CPL3-disabled control ESP. Its compile-time-gated instrumentation fingerprints exactly 512 bytes using FNV-1a64 at loader handoff, the kernel's `wallimg` attachment, and the first `wallimg` LBA 0 block read. It is read-only diagnostic instrumentation; FAT validation behavior was not changed.

The earliest demonstrated discrepancy is therefore **after the recorded loader handoff and by RAMDISK attachment**. The first sampled kernel attachment already has different bytes; the block-layer callback does not introduce a further fingerprint change. This does not establish whether the difference arose during the handoff/trampoline, address mapping, early kernel activity, or another operation before attachment. The fingerprint is a bounded 64-bit hash of the first sector, not a byte-for-byte trace or a full-image integrity check.

At mount, the FAT diagnostic reported device 1 (`wallimg`), sector size 512, initial LBA 0, two reads, first and last status `0x00`, and sector zero obtained. The guest saw signature `0x0000`; BPB fields read as zero, including bytes/sector, sectors/cluster, reserved sectors, FAT count, and FAT sizes. The first BPB rejection was `FAT32_BYTES_PER_SECTOR_REJECT`; the FAT16 probe also rejected bytes/sector; the final trace stage was `EXFAT_FILESYSTEM_TYPE_REJECT`. Thus the successful I/O status is not a successful filesystem mount.

The guest used the BootInfo v3 loader image and logged UEFI BootInfo magic `0x49425847` at `0x3E4B7000`; this kernel did not print a runtime BootInfo version field. It loaded and mapped a 64 MiB RAMDISK at `0x150DB000`. The kernel logged CR3 `0x3F801000` and a task-frame arena at `0x3CE28000` with 4,096 pages free; memory ownership was ready with user-mode disabled. CPL3 diagnostics were disabled in this candidate, and no CPL3 cycles or normal application launch were attempted. VFS root `/` did not mount and `/Apps` was absent. The desktop was drawn; its event loop and cursor were later reported active, and PIT heartbeat output continued through tick `0x170C`. The captured screenshot shows the desktop and taskbar with the expected filesystem-backed content unavailable.

This repeat with CPL3 disabled establishes that CPL3 is not required to reproduce this failure. The matching loader fingerprint and changed kernel attachment fingerprint narrow the observed boundary, but the run does not resolve why the divergence occurs or show whether CPL3 contributed to the separate CPL3-on run. No root cause or correction is established. The smallest useful next experiment, if another QAC run is separately authorized, is to add the same bounded fingerprint at the first kernel C entry and immediately after the relevant paging/CR3 transition. That would split the currently observed handoff-to-attachment interval without changing filesystem behavior.
