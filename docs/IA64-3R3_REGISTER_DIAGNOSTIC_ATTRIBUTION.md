# IA64-3R3 Register Readback Attribution

**Outcome: `IA64_REGISTER_DIAGNOSTICS_QUALIFIED`**

The `IVA=0x77` and `BSP=0x77` text from IA64-3R2 came from a broken hexadecimal reporting path. GCC-generated code kept live values in stacked register `r32`, while the inlined Ski SSC sequence also wrote `r32` and did not describe that write to the compiler. The resulting output repeatedly printed `0x77` regardless of the value supplied to `put_hex()`. An isolated Ski probe reads the expected IVA/BSPSTORE state and confirms the register accessors and Ski SSC `r8` return path. The SSC boundary is now a small assembly ABI function that allocates its input frame and restores `ar.pfs`.

No guideXOS kernel was executed during IA64-3R3. The final kernel candidate is statically qualified and remains marked unauthorized for guest execution.

## IA64-3R2 execution reconstruction

The preserved guest stdout is 213 bytes with CRLF line endings. It contains exactly:

```text
guideXOS IA-64 kernel init
  IVA = 0x77
  BSP = 0x77
  Interrupt collection enabled
IA-64 arch init complete
IA64-2 early-exec: SKI single-entry profile
Interrupts masked; scheduler and threads unavailable
```

`IVA = 0x77` begins at byte offset 30 (line 2), and `BSP = 0x77` begins at offset 44 (line 3). The raw bytes really contain the text `0x77`; the report does not reinterpret that text as a reliable register value. The first guest message establishes entry into the C-level kernel initialization path; `IA-64 arch init complete` establishes that `arch_init()` returned. The following early-exec status and deliberate exit establish the bounded stop-only path.

The simulator wrote separate 105-byte stderr:

```text
kernel exited with status 0
56606488 insts (0 faults), 0.70 sec, 81422762 i/s, 18869287 cycles, 3.00 ipc
```

The 40 rows in `instruction-counts.txt` reconcile to 56,606,488 instructions: summing the first of the final four numeric columns on each row gives exactly `56,606,488`; the other column totals are `18,867,918`, `67`, and `37,738,503`. The runner recorded `GUEST_EXIT_ZERO`, exit code `0`, `timed_out=false`, and 1.018 seconds elapsed. Ski’s batch output contains aggregate instruction statistics and guest console text, but no register dump or per-instruction IP trace.

The strings were written by the guest, but the digits were generated by the faulty formatter. IA64-3R2 therefore establishes that the guest reached its startup messages and exited cleanly; it does **not** establish that IVA or BSP actually contained `0x77`. In particular, the printed `BSP` comes from `AR.BSP`, not `BSPSTORE`.

## Diagnostic path and root cause

The baseline GCC 13.5.0 target disassembly for `ski_console::put_hex(unsigned long)` in the preserved candidate is at `0x33cd00`. It has no private stacked-register frame. It places a character in `r32` (`mov r32=r14` at `0x33cd30`), executes the SSC break (`break.i 0x80000` at `0x33cd3c`), then later computes digits from `r32` (`shr.u r14=r32,r14` at `0x33cd9c`). The SSC path also writes its argument to `r32`. GCC had no output or clobber describing that write, so the input value held live in `r32` was invalidated behind the compiler’s back. The reproducible legacy result is `0x77` for every tested value; the exact stale value depends on the live register contents at that point.

The old inline wrapper constrained the SSC function input to `r15` and listed only a memory clobber. Its emitted `mov r32=...` and `break.i 0x80000` still changed architectural integer registers that GCC was free to use for other values. The Ski source confirms that the break handler reads the SSC function number from `r15`; the SSC ABI uses `r32` for argument 0 and returns the SSC result in `r8`. The independent GETCHAR test below confirms that the legacy `r8` result itself was correct; it was the old `put_hex()` display of that result that printed `0x77`.

IA-64 conventions classify `r14-r31` as scratch, `r8-r11` as return-value registers, and `r32+` as stacked automatic registers. A procedure that writes a stacked input must first allocate a frame; procedures that allocate a frame must restore the prior `ar.pfs` before return. The implementation follows those rules rather than adding a contradictory inline-assembly clobber. See the [IA-64 Software Conventions and Runtime Architecture Guide](https://portal.cs.umbc.edu/help/architecture/24525601.pdf), sections 5.2, 6.1, and 8. Intel’s manual set identifies this guide as the software convention reference.

The current reader paths were audited:

- `read_iva()` reads `CR.IVA`; `read_cr<2>()` reads the same control register.
- `read_bsp()` reads `AR.BSP`, which can advance with calls/RSE activity and need not equal `BSPSTORE`.
- `read_bspstore()` reads `AR.BSPSTORE`; Ski requires `RSC.MODE=0` for `BSPSTORE` and `RNAT` accesses. The header now documents that requirement. The probe switches to enforced-lazy mode for these reads and restores `RSC=3` afterward.
- `read_ar<16>()` and `read_ar<19>()` exercise `AR.RSC` and `AR.RNAT`; `read_psr()` records relevant PSR state.
- The diagnostic writes a known aligned IVA, executes `srlz.i`, reads it through both `read_iva()` and `read_cr<2>()`, and restores its own IVT. Those IVA/RSE changes occur only in the independent diagnostic ELF.
- Kernel startup assembly, register initialization, scheduler state, and interrupt policy were not changed.

Ski 1.5.1’s `src/exec.tmpl.c` rejects reads or writes of `AR.BSPSTORE` and `AR.RNAT` when `RSC_MODE` is not zero. This matches the isolated test’s successful enforced-lazy read sequence and explains why the diagnostic explicitly changes RSC mode around those reads.

## Correction and regression

`kernel/arch/ia64/ski_console.cpp` now routes `ssc()` and `getchar()` through `guidexos_ski_ssc()` in `kernel/arch/ia64/ski_ssc.s`. The bridge:

1. receives SSC function and argument in C ABI `in0/r32` and `in1/r33`;
2. allocates two input registers plus one local register, making its input frame writable;
3. moves the function to Ski’s `r15`, moves argument 0 to `r32`, and executes `break.i 0x80000`;
4. returns Ski’s `r8` result unchanged and restores `ar.pfs` before returning.

The new `tests/ia64_ski_diagnostic/run.sh` builds two separate minimal system-mode ELFs: one against the baseline `ski_console.cpp` from the starting commit and one against the corrected code. Both are independent diagnostic programs, not the guideXOS kernel. With input `Q`, both return that byte through `r8`; the legacy program’s formatter displays it as `0x77`, while the fixed program displays `0x51`. Exact output comparisons also cover zero, `0x77`, `0x100000`, `0x4c6fe00`, `0x4c7fe00`, `0x123456789ABCDEF0`, `0xFFFFFFFFFFFFFFFF`, repeated calls, and a value kept live across console output.

## Remaining uncertainty and IA64-3R4 gates

The actual 3R2 register contents were not saved independently at the time of that run. Therefore this report does not claim that its live IVA/BSP values were sampled or that the old kernel had a verified runtime register snapshot. It establishes that the apparent `0x77` discrepancy was caused by the formatter and that the independent Ski/readback path behaves as expected.

IA64-3R4 should be a separately authorized, single-run kernel qualification using the pinned candidate hash and manifest above. Before launch, rerun the ELF, manifest, loader, Ski identity, and early-exec gates; explicitly authorize the runner; retain the one-CPU, 2 GiB address-space, 120-second CPU, and 60-second wall limits; and keep scheduling and external interrupts disabled. Capture raw guest stdout/stderr and the instruction-count report. Use a bounded Ski breakpoint/register dump around IVA setup/readback if those corrected diagnostics still disagree. Compare IVA with the configured IVT and BSP with the configured RSE backing-store range; record BSPSTORE/RNAT only under `RSC.MODE=0`, and do not require BSP to equal BSPSTORE. No later scheduler, interrupt-resume, device, desktop, multi-CPU, UEFI, or general-runtime work is included in that gate.
